# ADR-0071 — The documentation service is a projection that can be rebuilt: every revision is addressed by digest, every checkpoint and release is a view equal to the latest, one table with a composite key holds them behind the DynamoDB interface, and GraphQL and REST are generated from one model that any reader may call

## Context

**The corpus already keeps every revision of everything, and offers a reader one of them.** A record changes only by
a typed History row. A checkpoint is "one cut, never revised" (`checkpoints/README.md`). A derived document "is never
revised, a new one is written" (`derived/README.md`). A manifest is verified "against the tree it measured, not
against today's" (`manifests/README.md`). What a reader is given is the head of a branch on a carrier. To read the
Theory of Operation as it stood at G9, a reader runs `git diff` between two tags (`narrative/README.md`).

**The custodian asked that the documentation keep the whole of its life in reach** ⟨K10⟩: every revision, and every
checkpoint or release "equal to the latest". Equal is the hard word. A system that keeps old versions as downloads
beside a live site has kept them and has not made them equal.

**The custodian also set the service's shape**: a store that is an open-source alternative to DynamoDB with a
single-table, composite-key design ⟨K5⟩, a server offering GraphQL and REST ⟨K6⟩, and integration with any user
interface ⟨K7⟩.

**A store of documentation must not become a second record.** ADR-0005 §1 names three roles and one holder for each,
and makes the archive the system of record. A documentation store that held the only copy of a revision would be a
record nobody decided to keep. §1 settles that before anything else.

## Decision

### 1. The service is a projection, and it can be rebuilt

- **P-1. The service's store holds nothing that is not derived from the corpus at a commit, by a pinned program.**
  The unit files, the records, modules and policies they bind to, and the manifests are the sources. The archive of
  record keeps them (ADR-0073 §2, class C; Proposed). The service is not a system of record, in ADR-0005 §1's sense,
  for anything.
- **P-2. Dropping the store and ingesting again yields the same digests.** Every revision, every view manifest and
  every binding is content-addressed, so a rebuild is checked by comparing digests and not by trust in the rebuild.
  This is ADR-0069 §10.2's `results` rule, regenerate and compare, applied to a store.
- **P-3. The service decides nothing.** It admits no action, counts no vote and issues nothing. A unit it serves is
  a derived statement under ADR-0070 §1, and where it and a record disagree the record wins.

### 2. A revision is immutable and is addressed by its digest ⟨K10⟩

- **L-1. A unit's revision is the SHA-256 of its canonical bytes**: the unit's three levels, its bindings and its
  metadata in a fixed serialization. The digest identifies the revision. A number, a date and a commit locate it
  (ADR-0069 §9 C-5).
- **L-2. A revision is written once.** No operation edits or deletes one. A correction is a new revision.
- **L-3. Every revision of every unit is reachable** three ways: by digest; by unit and revision number, where the
  numbers of a unit run from 1 with no gaps; and by unit and a time, which returns the revision in force then.
- **L-4. Two revisions of a unit can be compared**, level by level and binding by binding, through the API (§7).
- **L-5. Nothing ages out.** There is no expiry, no tiering to a slower class a reader cannot reach, and no limit on
  the number of revisions kept. How long the sources themselves are kept is ADR-0074's schedule, class C.

### 3. A unit has a life, and every state of it stays readable ⟨K10⟩

| State | Meaning | How a revision enters it |
|---|---|---|
| **drafted** | Ingested from a commit and in no cut view. Shown in `latest` with the word *draft* | Ingest (§9) |
| **released** | Named by the manifest of a checkpoint view or a release view | The cut (§4) |
| **superseded** | A later revision of the same unit exists | The later revision's ingest. The earlier one is unchanged |
| **withdrawn** | The unit's newest revision says the unit is withdrawn, why, and what replaces it | A withdrawing revision. Earlier revisions and the views naming them are unchanged |

- **LC-1. The states are computed from revisions and views, and are not stored on the revision**, which is
  immutable. A revision released at G12 and superseded since is both, and each view shows it as that view saw it.
- **LC-2. Withdrawal is a revision, not a removal.** A unit found to be wrong is withdrawn with its reason. A reader
  who follows an old link reaches the old text under a line saying it was withdrawn, when, and by which revision.
- **LC-3. Staleness is separate from state.** A revision whose binding no longer matches its node is stale (ADR-0070
  §7). It may be drafted, released or superseded as well.
- **LC-4. Disposal is not a state.** A unit holds no cognitive payload (§10 H-1), so no erasure under ADR-0006
  reaches one, and the service has no path that destroys a revision.

### 4. A view is a manifest, and every view is equal ⟨K10⟩

**A view is a named manifest: for each unit it contains, one revision digest, with the corpus commit and the corpus
manifest it was cut against.**

| Kind | Named | Cut when | Changes afterwards |
|---|---|---|---|
| **latest** | `latest` | Never cut. It follows the newest ingest of the default branch | Yes. It is the only view that does |
| **checkpoint** | `G12`, and so on | With each Genesis Checkpoint, against the checkpoint's own manifest | Never |
| **release** | `DOC-<date>`, or a promoted release's digest | With each documentation release (ADR-0070 §8); after bootstrap, with each publication under ADR-0069 §8 | Never |

- **V-1. Every operation of the API takes a view, and none is defined for `latest` alone.** Listing, reading at a
  level, following a binding, searching and comparing behave the same in `G12` as in `latest`. The contract tests
  run once against `latest` and once against a cut view, and a difference fails them.
- **V-2. A cut view answers from the corpus as it stood.** A binding in view `G12` pins the digest its node had at
  that cut. The service shows the clause, module or policy text of that digest. It also says, as a separate fact,
  whether the node has changed since. It never rewrites a cut view to agree with today.
- **V-3. A cut view is written once**, under its manifest's digest, and a second write that differs is refused.
- **V-4. Views are never removed.** A view of a checkpoint that `checkpoints/README.md` later says is known to be
  wrong stays, and carries that statement as a notice. This is that README's own rule for the checkpoint.
- **V-5. Two views can be compared by set difference on digests**: units added, removed, and changed, as ADR-0069
  §3 I-5 classifies a corpus-root revision.
- **V-6. `latest` always says what it resolved to.** A response from `latest` carries the revision digest it
  returned, so that a reader can cite what they read and reach it again after `latest` has moved.
- **V-7. The checkpoints cut before this service exists get views of what was readable then** *(drafter's choice)*:
  the narrative, the two guides and the READMEs as each manifest measured them, as units with one level and no
  bindings, marked as backfilled. G1 and G2 predate git and are backfilled as far as `manifests/index.tsv` says they
  verify. The alternative, in Options, is that history starts at the first cut after the service is built.

### 5. The store is one table with a composite primary key and secondary indexes ⟨K5⟩

**The service's store is reached only through the DynamoDB data model and API**, so that the engine behind it can be
replaced without a change to the service (§6).

- **S-1. One table.** Every item has a partition key and a sort key, and its type is read from the two together.
  Items that are read together share a partition, so that one query returns them in sort-key order.
- **S-2. Every access pattern is a key condition.** Each operation of §7 is a `GetItem` or a `Query` on the table
  or on one index, with a partition key and a range of the sort key. **No operation scans.** Annex A lists the
  patterns and the keys that serve them, and a pattern that cannot be listed there is not offered.
- **S-3. Secondary indexes carry the other readings.** A global index re-keys an item under a second partition and
  sort key, and a local index gives a partition a second sort order. Annex A uses two global indexes and one
  local one.
- **S-4. Immutability is a conditional write.** A revision and a cut view's entries are put with a condition that
  the key does not exist. An attempt to overwrite fails at the store, and does not rely on the service's code.
- **S-5. A view is cut in one transaction, or under a marker.** A cut view becomes visible only when all its entries
  are written. Where the engine has multi-item transactions, the cut uses them in batches. Where it has none, the
  view's head item is written last, and a view without its head is not served.
- **S-6. The engine is open source**: its licence is one the Open Source Initiative approves, and the build the
  reference runs is pinned by digest ⟨K5⟩.

### 6. The reference's engine is ExtendDB on PostgreSQL, and the interface is what is fixed

**The reference runs ExtendDB, AWS's Apache-2.0 implementation of the DynamoDB API, with PostgreSQL as its storage
backend** *(drafter's recommendation; the custodian named the requirement and no product)*.

- **What supports it.** It implements the interface §5 fixes, with composite keys, global and local secondary
  indexes, conditional writes and multi-item transactions, as its README and its differences document state. Its
  licence and PostgreSQL's are both OSI-approved. It is written in Rust, as the reference mechanism is.
- **What does not.** It is new. AWS's announcement calls it "a v0.1 release for development, testing, and
  experimentation", and its README scopes its 1.0 to "Local development and continuous integration (CI) test runs"
  and says it is not "A multi-server deployment". **Nothing in this corpus has run it.**
- **Why that is tolerable here.** The store is a projection (§1). An engine that loses data or stops costs the
  service its availability until a rebuild, and costs the record nothing. The same engine under the archive's
  index is argued separately, in ADR-0075 §4.
- **Substitution.** A deployment may put any engine behind §5's interface: ScyllaDB's Alternator, Amazon DynamoDB
  itself, or another. It declares which, as ADR-0033 §2's substitution rule has a deployment declare any substrate
  the reference chose. An engine that is not open source meets §5 except S-6, and the declaration says so.

Options lists the engines considered, and why each was not the reference's.

### 7. One model, two generated interfaces ⟨K6⟩

- **A-1. The API is described once**, in a model file in the repository. The GraphQL schema and the OpenAPI
  description of the REST interface are both generated from it by a pinned tool, and neither is edited by hand.
- **A-2. The two interfaces are equal.** Every type, field and operation reachable through one is reachable through
  the other. A generated parity test fails the build when one interface offers what the other does not.
- **A-3. The API reads and never writes.** There is no mutation in GraphQL and no method but `GET` and `HEAD` in
  REST. Content enters by ingest (§9) and by no request.
- **A-4. Every response names its view and its revision digests** (V-6). A response from a cut view, or for a
  revision by digest, is immutable: its entity tag is the digest and it may be cached without limit. A response
  from `latest` is cacheable briefly.
- **A-5. The operations are these**, in both interfaces:

  | Operation | Returns |
  |---|---|
  | List views; read a view's head | Kind, cut date, commit, manifest digest, counts |
  | List a view's units, filtered by audience, domain and kind (ADR-0070 §2, §3, §6) | Unit heads with their state in that view |
  | Read a unit in a view at a level | The content tree of MI, SI or DI, its marks, its bindings, its staleness |
  | List a unit's revisions; read one by number, digest or time | L-3 |
  | Compare two revisions, or two views | L-4, V-5 |
  | From a node of the specification graph, list the units bound to it in a view | ADR-0070 §5's bindings, read backwards |
  | Search a view | Units, with the level and passage matched |

- **A-6. The interface is versioned, and a version only grows.** A field is added, or deprecated with a date, and
  not repurposed. A breaking change is a new version served beside the old.
- **A-7. A request cannot exhaust the service by its shape.** Lists are paged by cursor. A GraphQL query is bounded
  in depth and cost, and the bounds are in the schema's description. This protects availability and nothing else.
- **A-8. Search is a second projection, built per view.** A cut view's index is built once at the cut and is
  immutable with it, which is how V-1 holds for search. The index is rebuilt from the store as the store is from
  the corpus (P-2).

### 8. Any reader may integrate, and none is privileged ⟨K7⟩

- **U-1. The reference reader has no interface of its own.** It uses §7 and nothing else (ADR-0072 §1 R-1). What it
  can show, any client can show.
- **U-2. Content is returned as a tree and not as markup.** A level's body is a typed tree of headings, paragraphs,
  lists, tables, code, figures, notes and binding references. A client renders it in its own components. A rendered
  HTML fragment of the same tree is offered beside it as a convenience, and the tree is the contract.
- **U-3. The fields accessibility needs are part of the tree and are mandatory**: a figure's short alternative and
  long description, a table's header cells and caption, a heading's level, the language of the unit and of any
  passage in another, and the expansion of an abbreviation on first use. Ingest refuses a unit that lacks one
  (ADR-0070 §8). A client cannot be accessible on content that omits them, which is why they are not left to it.
- **U-4. Marks and bindings are data, not decoration.** A unit's status marks and each binding's node, clause,
  digest and freshness are fields. ADR-0070 §5 obliges any reader that shows a guarantee to show its mark, and this
  is what lets one do so.
- **U-5. A client may be a page, an application, a terminal or a program.** Cross-origin reads are allowed for the
  public units. An embeddable element is one such client (ADR-0072, Options).
- **U-6. Who may read is the deployment's rule.** The archetype's units are public, under `LICENSE-DOCS`. A
  deployment's own units (§10) may be restricted, and the service asks the deployment's identity provider. A
  restriction hides a unit from a reader and changes no unit.

### 9. Ingest is the only way in, and it starts on a digest

- **I-1. Ingest reads the corpus at one commit and writes revisions, bindings and, for `latest`, a manifest.** It is
  a program in the repository, named by digest, that runs the same way by hand and on a carrier (ADR-0069 §6 G-1).
- **I-2. Ingest refuses a name.** It is given a commit, resolves it to a tree, and records the tree's digests. A
  cut is given the checkpoint's or the release's manifest and refuses a tree that does not verify against it
  (ADR-0069 §1 P-1).
- **I-3. Ingest is idempotent.** Run twice on one commit, it writes nothing the second time (S-4).
- **I-4. Ingest runs the gates of ADR-0070 §8 first**, and writes nothing for a unit that fails one.
- **I-5. A carrier's merge is not a cut.** Merging to the default branch moves `latest`. A checkpoint view is cut
  when the custodian cuts the checkpoint, and after bootstrap a release view is cut when a promotion's publication
  names it (ADR-0069 §8, §9 C-1).

### 10. What the service does not hold, and a deployment's own units

- **H-1. No cognitive payload and no labelled item** (ADR-0004; ADR-0047 §1). A unit is authored text about the
  system. An example in a unit is written for it and is not taken from a round.
- **H-2. No secret and no deployment value**, in the archetype's units. Where a deployment must supply a value, the
  unit says so in the words the Adopter's Guide uses, "the deployment writes this".
- **H-3. A deployment's documentation is an overlay on the archetype's** *(drafter's choice)*. It keeps, replaces,
  adds or omits units by id, as ADR-0058 §1 (Proposed) has a deployment's specification graph relate to the
  archetype's. A replaced unit names the archetype revision it replaces, so that a change upstream shows as stale.
  The overlay's views are the deployment's own, and are cut against its declaration.

### 11. Degeneracy and the trusted base

**No degeneracy is declared, and no row is added.** No theorem takes a premise from the service. By ADR-0045 §2's
test, its failure produces no admit, promotion or issuance. It can show a reader a wrong or missing page, and
ADR-0070 §11 says what bounds a reader who acts on one. A deployment that serves its documentation some other way
has made no declaration under ADR-0023 by doing so. It has only not met this record.

### 12. Ratification condition

- **The service exists**: ingest, store, both interfaces and search, with `latest` and at least two cut views.
  **Not met: nothing is built.**
- **P-2 is seen:** the store is dropped and rebuilt, and every revision and view digest is the same. **Not met.**
- **§2 and §4 are seen:** a revision is refused an overwrite at the store (S-4); a cut view is refused a second,
  different write (V-3); the contract tests pass identically against `latest` and a cut view (V-1); a binding in a
  cut view returns the node's text at that cut after the node has changed (V-2). **Not met.**
- **A-2's parity test exists and passes**, and the GraphQL schema and OpenAPI description are generated from one
  model with no hand edits. **Not met.**
- **Annex A covers §7**: every operation of A-5 is a row with a key condition, and no operation scans (S-2).
  **Not met: Annex A lists them, and nothing has run a query.**
- **The engine of §6 is run under the service's load and a rebuild**, and its build is pinned. **Not met. Nothing in
  the corpus has run ExtendDB.**
- **A second client that is not the reference reader renders a unit from the API** (U-1). **Not met.**
- **ADR-0070 is ratified, or this record is ratified with it.** **Not met: it is Proposed.**
- **A reader who is not the drafter** (ADR-0029 A2). **Not met.**
- **The custodian's reading of every drafter's choice and recommendation**, the engine among them. **Not met.**

**The store's engine** ⟨K5⟩. "Open source" is read as an OSI-approved licence on the releases a deployment would
run today. Composite key means a partition key with a sort key, and secondary key means an index that re-keys an
item. Except where the provenance note says a page was read, each row is the drafter's understanding and was not
checked.

## Consequences

**Positive**
- **A link to a page in a checkpoint keeps working and keeps meaning the same thing.**
- **Old and new are served by one code path**, so the old cannot rot unnoticed: the same tests run against it.
- **The store can be lost.** A rebuild is a recomputation with a check, not a restore.
- **Two engines can stand behind one interface**, and the choice of the first is cheap to reverse.
- **A deployment's reader, a terminal client and the reference reader are peers.**

**Negative**
- **Everything is kept, so the store only grows.** Its size is the number of revisions and not the size of the
  current documentation.
- **A search index per view** multiplies with the number of cuts.
- **A single-table design fixes the access patterns in advance.** A new way of reading is a new index or a new
  item type, and Annex A must change before the API can.
- **The recommended engine is months old and declares itself unfit for production.** §6 argues this is tolerable
  for a projection. It is still the least proven part of this record.
- **Two interfaces are twice the surface to test**, and A-2's parity is a standing cost.
- **Backfilled views (V-7) are thinner than cut ones**, and a reader must be told so on every page of them.

## Open obligations

- **The model language and generator of A-1**, pinned. TypeSpec, Smithy and Protocol Buffers with generators for
  both interfaces are candidates. Not chosen.
- **The canonical serialization of L-1.** A revision's digest depends on it, and it must not change once a view is
  cut.
- **The service's language.** Rust is the drafter's recommendation, with the mechanism's pinned toolchain.
- **The search index of A-8**, and how passages at three levels are ranked.

## Annex A — The table's keys (reference design)

*(Drafter's choice throughout. This annex is the reference's design and not a requirement. §5 is the requirement.)*

One table. `PK` and `SK` are the partition and sort keys. `n` is a revision number, zero-padded to eight digits so
that it sorts. `d` is a SHA-256 in hex.

| Item | `PK` | `SK` | Holds |
|---|---|---|---|
| Unit head | `UNIT#<unit>` | `HEAD` | Title, kind, audiences, domain; the newest `n` (the one attribute rewritten, with `latest`) |
| Revision | `UNIT#<unit>` | `REV#<n>` | `d`, time ingested, source commit and path, withdrawal reason if any |
| Level body | `REV#<d>` | `LVL#<MI\|SI\|DI>#<part>` | The content tree, split into parts under the item size limit |
| Binding | `REV#<d>` | `BIND#<level>#<seq>` | Node id, clause or path, pinned digest, relation, reader |
| Node entry | `VIEW#<view>#NODE#<node>` | `UNIT#<unit>#<level>#<seq>` | One for each binding of each revision a view names. `d`, pinned digest, relation |
| View list entry | `VIEWS` | `<kind>#<date>#<view>` | The view's name. Written at the cut |
| View head | `VIEW#<view>` | `HEAD` | Kind, cut date, commit, corpus manifest digest, view manifest digest. Written last (S-5) |
| View entry | `VIEW#<view>` | `UNIT#<unit>` | `d`, `n`, state in the view |
| Catalogue entry | `VIEW#<view>` | `CAT#<audience>#<domain>#<kind>#<unit>` | One per audience of the unit. Title and `d` |
| Ingest | `INGEST` | `AT#<time>#<commit>` | The manifest digest `latest` resolved to at that ingest |

| Index | Partition key | Sort key | On |
|---|---|---|---|
| **GSI1**, domain within a view | `VIEW#<view>#DOM#<domain>` | `AUD#<audience>#<kind>#<unit>` | Catalogue entries |
| **GSI2**, revision to views | `REV#<d>` | `VIEW#<view>` | View entries |
| **LSI1**, a unit by time | `UNIT#<unit>` | `AT#<time>` | Revisions |

| Operation (§7 A-5) | Key condition |
|---|---|
| List views | `Query` `PK = VIEWS` |
| A view's head | `GetItem` `VIEW#<view>`, `HEAD` |
| A view's units for an audience | `Query` `PK = VIEW#<view>`, `SK begins_with CAT#<audience>#` |
| A view's units for a domain, then audience | `Query` GSI1 `PK = VIEW#<view>#DOM#<domain>`, `SK begins_with AUD#<audience>#` |
| A unit in a view at a level | `GetItem` `VIEW#<view>`, `UNIT#<unit>` for `d`; then `Query` `PK = REV#<d>`, `SK begins_with LVL#<level>#`; then `Query` `PK = REV#<d>`, `SK begins_with BIND#<level>#` |
| A unit's revisions, newest first | `Query` `PK = UNIT#<unit>`, `SK begins_with REV#`, descending |
| A revision by number | `GetItem` `UNIT#<unit>`, `REV#<n>` |
| A revision by digest | `Query` `PK = REV#<d>` |
| A unit's revision at a time | `Query` LSI1 `PK = UNIT#<unit>`, `SK <= AT#<time>`, descending, limit 1 |
| The views a revision is in | `Query` GSI2 `PK = REV#<d>` |
| Units bound to a node, in a view | `Query` `PK = VIEW#<view>#NODE#<node>` |
| Compare two views | Two `Query` calls, `PK = VIEW#<a>` and `PK = VIEW#<b>`, `SK begins_with UNIT#`, merged by unit |
| What `latest` was at a time | `Query` `PK = INGEST`, `SK <= AT#<time>`, descending, limit 1 |

Search (A-8) is not a key condition. It is its own projection and is not in this table.
