# ADR-0048 — A Thinker learns its tools from the mechanism: the allowlist entry carries its interface, and the Listener delivers it

**Status:** Proposed · 2026.10.03
**Status note:** Confirmation required under **C4** (it answers the second half of CR-32 and part of ADR-0040's open
obligation on the entry's schema) and, on the drafter's reading, **C3**: ADR-0043 §1 and ADR-0042 §4 call Run's
ingress a closed list of three, and §2 makes it four. The list stays closed; a ratified sentence that says "nothing
else" is still changed. C1 does not apply: no privileged path is touched. C2 does not apply: no confinement claim is
made. **No seat gains a variant**, and no principal changes containment class.
**Pending:** none.
**Deployment position:** Archetype. One degeneracy, D-0048-1 (§7), which is the reference today.
**Depends on:** ADR-0040 §3 (the Run allowlist), ADR-0022 §3 (the Build allowlist), ADR-0043 §1 and ADR-0037 §2 (the
Listener and what it delivers), ADR-0044 (a bundle is trusted by its signature), ADR-0031 §4 and R2 (a lease narrows;
a new bundle reaches a principal at its next grant), ADR-0007 (a mechanical rendering is a syntactic lift)
**Relates to:** ADR-0049 (the entry's one schema), ADR-0047 (labels on ingress; the entry's label, destination and
outward declarations), ADR-0034 A2
(the entry's channel declaration, pending), ADR-0018 and ADR-0043 §3 (the decoder), ADR-0016 (the Persona),
ADR-0035 §1 (what a round consumed)
**Closes:** nothing until ratified. On ratification: the tool-description half of CR-32.
**Carries a debt against:** ADR-0040 §3 and ADR-0022 §3 (the entry gains an interface) · ADR-0043 §1 and ADR-0042 §4
(the closed list gains an item) · ADR-0042 §3 (the round topic gains an opening record) · ADR-0043 §4 (what an

`consumed`; its R6) · ADR-0033 (an addendum)

---

## Context

CR-32 says tool descriptions are unpinned: TOPAK pins a tool's code by digest, and the text a Thinker reads about the
tool is ingress that no allowlist entry names. Reading the reference shows the gap has a different shape.

- **The alphabet's descriptions are compiled into the mechanism.** A Run Thinker is offered `consult`, `actuate` and
  `report`, each with a fixed string (`server.rs` `tools_for`). Those change only with a mechanism release.
- **An allowlisted tool has no interface text anywhere on the record.** A bundle entry carries the tool's name and
  digest, the types of its inputs and, for Run, its channel (`policies/data.json`). `actuate` takes a tool, a digest
  and an object of inputs.
- **The types are enforced and nothing is described.** `tool_schema.rego` checks an input's type. Nothing tells a
  Thinker what a tool is for, what an input means or what comes back.

So a Thinker cannot learn from the mechanism which tools its lease may call. It learns from its Persona's prompt, from
the task, or from something it consults. **In each case nothing binds the text to the entry's name and digest.**

| Where the text comes from today | What is wrong with it |
|---|---|
| The Persona | Pinned with the Persona, and stale as soon as a tool is promoted again under a new digest |
| The task | Set per grant on the operator channel, which the corpus does not type (CR-34) |
| A consulted object | Pinned content that nothing says describes the entry it claims to |

**The MCP "rug-pull" cannot happen here**, because no tool supplies text at run time. What is missing is a binding,
not a pin. The custodian's decision is that the mechanism supplies it.

---

## Decision

### 1. An allowlist entry carries its interface

**Every allowlist entry, in Build and in Run, carries an interface: what a Thinker needs to know to call the tool.**
This section says what the interface must hold. **The definitive statement of the entry, its fields and its load
checks is ADR-0049** ⟨R2⟩; the table below is a reading of it.
It is bundle data, covered by the bundle's signature (ADR-0044) and promoted with the entry.

| Part | What it is | Checked by anything? |
|---|---|---|
| Name and digest | As today (ADR-0022 §3; ADR-0040 §3) | Yes: the admit path |
| Inputs | Each input's name and type, as today | Yes: the bundle tier |
| **Purpose** | One text field: what the tool does and what it returns | **No.** It is a claim, as a channel declaration is |
| **Input notes** | One text field per input: what the input means | **No** |
| Channel, in Run | Its kind, and whether the entry is outward (ADR-0047 §7) | The channel's owner (ADR-0034 A2, in force since Batch 30) ⟨R5⟩ |
| Labels | The entry's result label, its destination inputs and what each input accepts by handle (ADR-0047) | The floor's load checks (ADR-0047 F4 to F6) |

- **The text is in the bundle, not behind a reference** *(drafter's choice)*. One signature covers the entry and its
  text, and there is no second object to resolve or to go missing.
- **The text is bounded in size** *(drafter's choice)*, by a mechanism parameter. A description is not a place to
  carry a corpus.
- **A bundle in which an entry has no purpose text is not well-formed and does not load** *(drafter's choice)*. This
  is the same totality rule ADR-0047 §1 applies to labels.
- **The interface has no digest of its own in any record.** It is fixed by the bundle revision, which every grant
  already names.

### 2. The Listener delivers the tool list at the start of a round

**The Listener delivers, once, the interface of every entry the lease may call.** It is a fourth item of ingress,
beside the task, consulted content and tool results, and the list of ingress stays closed.

- **It is a function of the grant.** The grant names the bundle revision and the lease's narrowing (ADR-0031 §4). The
  tool list is the allowlist of that revision, narrowed by that lease. It needs no admit: a reader with the log can
  recompute it.
- **The mechanism writes it to the round topic as the round's opening record** ⟨R1⟩ *(drafter's choice)*. The
  principal does not write it and cannot, as with an `Actuate` record (ADR-0042 §3). Its envelope carries the digest
  of the rendered list and the bundle revision; its payload is the rendered list. It has no sequence number, because
  it is not an effect, so it is outside what a watermark covers.
- **An Observer is given its Thinker's list** ⟨R1⟩ (the custodian's decision). It reads the opening record under
  `W(p)`, as it reads every other record on that topic, and so does the correlator. An Observer can then judge a call
  against what the Thinker was told the tool was for. It is given the list; its mark does not assert that it read it.
- **A Build round's tool list is `ingress` and `consumed`** ⟨R1⟩ (the custodian's decision), as the object the
  opening record's digest names. It is text the round's model read. ADR-0035 §1 carries the rule at its R6.
- **It is exact.** The list holds every entry the lease may call and no entry it may not. A Thinker is not shown
  tools another lease holds.
- **It is rendered by the mechanism in a fixed form.** The rendering is mechanical and total over the entry's
  fields, so it is a syntactic lift (ADR-0007). The Listener still makes no choice.
- **It cannot change inside a round.** A new bundle reaches a principal at its next grant (ADR-0031 R2), so the list a
  Thinker was given is the list its admits are decided against.
- **It is not an effect and is not counted against `R`.** It is delivery, as the task is.
- **The channel is delivered by kind and by whether it is outward, without its target** *(drafter's choice)*. A
  Thinker needs to know that a call leaves the deployment, which ADR-0047's F1 to F3 will hold it to. It does not
  need the address.
- **Under ADR-0047 the list is delivered clear and carries neither reserved name.** It is the bundle's own text and
  passed promotion. It adds nothing that F1 to F3 read.

### 3. The mechanism's list is the only description with standing

- **A Thinker's tools are the ones on its list**, named as the list names them. The list supplies the name and digest
  an `Actuate` or `Invoke` must carry, so a Thinker does not need either from anywhere else.
- **What a Persona, a task or a consulted object says about a tool is content.** The mechanism does not read it and
  no admit turns on it. A Persona need not carry tool descriptions, and one that does is not checked against the
  list: a Thinker is havoc, and what it believes about a tool changes nothing the admit path decides.
- **A task says what to do. The list says what there is to do it with.**
- **Promoting a tool no longer makes a Persona stale.** The next grant delivers the new entry's interface. What a
  Persona still owes is a decoder that can emit inputs of the declared types, which is decoder–alphabet compatibility
  (G5 item 17) and is not settled here.
- **The alphabet's own descriptions stay in the mechanism.** They describe variants, not tools, and change with a
  release.

### 4. How it changes

| What changes | Where it lives | How it changes | When it takes effect |
|---|---|---|---|
| An entry's purpose text or input notes | Bundle data | Bundle promotion, signed | At a principal's next grant |
| Which entries a lease may call | The lease | Per grant | That round |
| The rendering; the size bound | Mechanism | A mechanism release | At deployment |

**A description that carries an injection has to pass promotion.** That is the gain over text arriving in a task or a
Persona's prompt: it is drafted, gated and voted on like any bundle change, and it is on the record by revision.
Promotion is as strong as its gates, and at the reference gate evidence is an operator's assertion (G8).

### 5. What this record does not cover

- **A wrong description.** Purpose text is a claim. A tool described as read-only that writes is not detected by
  anything here. The channel declaration and the labels are what bound it.
- **A description written to steer.** Text that passed promotion and still misleads a Thinker is a promotion finding
  or an Observer finding. It is a judgment about content and not a lift.
- **Tool results.** They are ingress with labels (ADR-0047).
- **Tools outside the deployment's allowlist**, such as an MCP server the mechanism does not own. ADR-0040 leaves
  that to a degenerate rung, and so does this record.
- **Whether a Persona works with a given list.** A list a Persona cannot use produces refusals, not harm.

### 6. Where the three declarations meet

The allowlist entry is now asked for by three texts: its channel (ADR-0034 A2, in force since Batch 30 ⟨R5⟩), its labels and destination
inputs (ADR-0047, Proposed), and its interface (this record). **They are one schema and are written once**, in ADR-0049 ⟨R1⟩,
Proposed the same day. This record says what the interface part must hold; ADR-0049 §1 and §6 give its fields and the
check that refuses an entry without them.

## Options considered

| Option | Disposition |
|---|---|
| **Leave descriptions to the Persona, and say so** | Rejected, by the custodian's decision. The text is pinned and then stale, and a tool promotion becomes a Persona compatibility question |
| **The entry names a content address and the Thinker consults it** | Not taken *(drafter's choice)*. It adds no kind of ingress, which is its merit. The Thinker still has to be told the reference, and it cannot enumerate its tools |
| **Carry descriptions in the task** | Rejected. The task is per grant on the operator channel, the least typed surface in the corpus |
| **A tool describes itself at run time** | Rejected. This is the rug-pull: text the mechanism did not promote, changed by the party it describes |
| **Each allowlisted tool as its own entry on the MCP surface** | Not taken. ADR-0040 keeps a three-variant alphabet and declined a wire-level vocabulary at the archetype. The list is content delivered to the Thinker, not a change to what it may say |
| **The Observer recomputes the list from the log** | Not taken *(drafter's choice)*. It can, and a facts-only reader cannot: it would need the bundle and the renderer. A record on the topic is read under the ACL every Observer already has |
| **Deliver the list to the Observer by a stage of its own** | Not taken. An Observer has no Listener (ADR-0043 finding 3), and this record does not give it one |
| **A variant that asks for the list** | Not taken. The list is fixed for the round, so asking adds an admit and tells the Thinker nothing new |
| **Deliver the channel's target** | Not taken *(drafter's choice)*. Whether a call is outward is what the Thinker needs. The custodian may prefer the target; nothing else depends on it |
| **Run only** | Not taken *(drafter's choice)*. Build's `Invoke` has the same entry, the same data file and the same gap |

## Consequences

**Positive**
- **A Thinker can enumerate its tools**, which it cannot do today.
- **An Observer knows what its Thinker was told**, from the same record, and a facts-only reader can see by digest
  that two cells were given the same list.
- **A description is bound to the entry it describes**, by one signature, and is on the record by revision.
- **Text a Thinker reads about a tool has passed promotion**, where today it may arrive by any path.
- **A tool promotion stops being a Persona change.**
- **The Thinker is told which calls are outward**, so the refusals of ADR-0047's F1 to F3 are not a surprise to it.

**Negative**
- **The closed list of ingress is opened by one**, and two ratified records say three.
- **The round topic gains a kind of record with no sequence number**, written by the mechanism before any effect.
  ADR-0042 §3 has no such record today.
- **Every Build lineage under one bundle now shares an object.** The tool list is `consumed`, and it is the same text
  for every round the same lease shape is granted. It adds to exact overlap between lineages that are otherwise
  independent. The direction is the safe one, toward refusal, and the amount is small beside a corpus; it is still
  systematic (Open obligations).
- **Every round carries the list**, which is tokens on every grant and more for a wide lease.
- **Purpose text is unchecked prose in a signed bundle.** A reviewer at promotion now reads prose aimed at a model,
  and the gates have nothing to say about it.
- **Bundle authors must write for a model.** A poor description costs refusals and wasted rounds.
- **The rendering is mechanism code** that every Thinker's view of its tools now rests on.
- **One author, two days.** The module and its proof are the drafter's as well (§8).

---

## Findings

1. **The reference has no description for any allowlisted tool.** CR-32 and the competitive assessment describe the
   gap as text that is not pinned. At the reference it is text that does not exist on the record.
2. **A Thinker cannot ask what it may call.** No variant and no delivery tells it. The e2e fixtures know the tool names
   because their authors did.
3. **Three texts need the allowlist entry's schema at once** (§6). ADR-0040 finding 4 said the entry is where the
   vocabulary grew; it has kept growing.
4. **The enforced half of the interface was always in the bundle.** Input types are checked by `tool_schema.rego`.
   This record adds the half that is read and not checked, and says which half is which (§1).
5. **The list is ingress, and lineage counts ingress.** In Build a tool list is text a round's model read. The
   custodian settled it at R1: `ingress` and `consumed` (§2), consistent with ADR-0047 §3's rule that an item
   delivered clear is `consumed`.
6. **Giving the Observer the list needed somewhere to put it.** An Observer's ingress is the topic it watches, by the
   ACL (ADR-0043 finding 3). Writing the list to that topic uses the path that exists. It also puts the list inside
   the round's unit of erasure, which costs nothing: the list can be recomputed from the bundle.

- **The rendering's form**, and the size bound's value.
- **Shared text and the overlap measure.** Whether ADR-0035's E3 should set mechanism-rendered objects aside, or its
  θ values simply be set knowing they are there.
- **A gate for purpose text**, if one can be stated without a judgment: for example that it names every input.
- **Decoder–alphabet compatibility** (G5 item 17), which this record narrows and does not settle.
- **The reference** (§8), and tests there for what the module leaves out: the rendering, the size bound, and the
  load check on purpose text.
- **Rows for `spec/ToolList.tla` in `spec/theorem-premise-binding`.**
