# ADR-0036 — At rung 1 the launcher is the channel: the reference's guest launcher, its profile, and a principal `Mediated` by declaration

**Status:** Proposed · 2026.09.28
**Status note:** Confirmation required under **C2** (a confinement claim: §2 says how ADR-0034 §3.5's session binding
is realized at rung 1, and §4 declares which profile clauses a real guest meets) and **C4** (resolves, in part,
ADR-0034's obligation for the reference). C3 does not apply: nothing here reverses an accepted record. ADR-0034 §4's
criterion conjunct is not touched, so **no principal in this record is `Contained`**, and none is claimed to be.
**Pending:** none.
**Deployment position:** Rung 1, which is D-0034-2. The first profile (§4) fails P3, which is D-0036-1 (§8). Every
principal this record launches is `Mediated` by its profile, not by the absence of one.
**Depends on:** ADR-0034 (rungs, the profile clauses, appraisal at grant, no silent downgrade, `Contained`),
ADR-0031 (the lease's `confinement` field; A1, renewal keeps the rung), ADR-0033 (the reference, the front door,
I14's bearer token), ADR-0022 §1 (the alphabet the occupant speaks), ADR-0017 (in-house provenance)
**Relates to:** ADR-0035 (lineage projection; finding 1), ADR-0024 (promotion of the profile, §6), ADR-0029 (TCB
rule), ADR-0028 F2 (stop attribution)
**Closes:** nothing yet. On ratification, the first half of ADR-0034's reference obligation: a launcher, a profile,
a guest image and the session binding exist. The second half, `is_contained()` reachable, waits on ADR-0035
**Carries a debt against:** ADR-0033 (§6: moving the launcher into `topak-node` is a change under `mechanism/`
and needs an addendum) · ADR-0035 (finding 1) · the TCB declaration record (§5's rows)

## Context

ADR-0034 defined rungs 1–3 and the seven profile clauses, checked them in TLC, and left the reference where ADR-0033
put it: every lease at rung 0, every principal `Mediated`, the sandbox gap (`mechanism/` G1) concrete and unclosed.
Its open obligations name the smallest step, "a rung-1 launcher in `topak-node`", and what it needs: a profile, a
guest image and the session binding.

Two things exist that the corpus has not looked at.

**A guest image.** `slm/serve/` runs a trained checkpoint in a container with no network, a read-only root, no
capabilities, a non-root user, the three bundle files mounted read-only and their digests checked at start, and
stdio as its only channel. It was built as an MCP *server*: it offers the model as a tool called `generate`. In the
corpus's terms that is the wrong role. A tool a principal `Invoke`s is native, and D-0034-3 makes the principal
`Mediated` on that alone. The same container holding the same weights in the other role, the occupant that speaks
the front door, is the shape both 09.27 notes asked for: "a minimal inference loop that speaks the six MCP tools
over one channel".

**A front door with no way in from a guest.** ADR-0033's front door is `topak mcp`, a stdio MCP server the agent
process runs, which proxies to the node's Unix agent socket as JSON lines carrying a bearer token (I14). A guest
that speaks it needs the socket. On Docker Desktop, the reference's host, a Unix socket cannot be bind-mounted into
a container; the platform's file sharing does not carry sockets. So a guest on this host has exactly one channel
available, stdio, and something on the host must join it to the socket. That constraint and ADR-0034 §3.5's rung-1
sentence, "the launcher binds the session and is trusted to", are the same fact seen from two sides.

**What a first pass should claim.** The feasibility note's advice stands: build the `Mediated` principal first and
name its channels, so that the verdict is derived from a declared profile rather than from the absence of one.
ADR-0034 §4 now makes `Contained` wait on ADR-0035 in any case, so nothing this record launches can be `Contained`,
and the record does not try. What it can do is make every conjunct of §4 except the criterion **checkable on a
running guest**, and state on its face which profile clauses the guest fails.

## Decision

### 1. The profile is a file whose digest is the lease's confinement digest

A **confinement profile** (ADR-0034 §1) is realized as a JSON artifact with these parts:

| Part | Content |
|---|---|
| `image` | The guest image, by content digest. Not a tag |
| `launch` | The exact runtime constraints the launcher applies: network, root filesystem, capabilities, user, IPC, process and resource limits, the mounts and their modes. The launcher applies these and nothing else |
| `channel` | The one channel, and its protocol (§2) |
| `persona` | The Persona bundle's reference values: the digest of `model.json`, which in turn pins the weights and tokenizer (P5, P7) |
| `clauses` | **P1–P7, each `pass`, `fail` or `vacuous`, with a one-line reason.** A profile that omits a clause is malformed |
| `subtractions` | For each `fail`: what would have to be removed for it to pass |

**The digest of the file is the first element of the lease's `confinement` field** (ADR-0031 §1). A grant at rung
≥ 1 names a profile that exists; the launcher refuses to launch a digest it cannot resolve to a file.

**A profile declares what it fails.** ADR-0034 §3.4 forbids silent downgrade: a principal whose evidence does not
reach the declared rung is refused. A profile that declares P3 `fail` is not a downgrade. The rung is about how the
mechanism's belief in the profile was established, and rung 1 is "asserted by the launcher"; the profile is about
what the guest is, and this one says on its face that an interpreter is reachable inside it. **A grant at rung 1
on a profile with a declared failure is valid, and the principal is `Mediated` by ADR-0034 §4**, because P3–P5 do
not all hold. That verdict is computed from the profile and can be tested, which is what distinguishes it from the
rung-0 verdict, which is computed from nothing.

**In the reference the profile is a file under `slm/serve/`**, cited by digest in the results. In the mechanism it
is a promoted Build artifact (ADR-0034 §1, ADR-0024). The difference is §6.

### 2. At rung 1 the launcher is the channel

The launcher does four things, in this order, for one grant:

1. **Launch.** Start the guest from the profile's image with the profile's constraints, with stdin and stdout
   held by the launcher. The guest loads the Persona bundle, checks the bundle's digests against `model.json`, and
   writes its identity (the `model.json` digest, family, parameter count, `root`) as its first line. A guest that
   cannot verify its bundle exits without writing it.
2. **Appraise.** Compare the running image's digest and the guest's reported `model.json` digest with the profile's
   reference values (P7). Both match: **Attested**, by the launcher's own assertion, which is what rung 1 means
   (ADR-0034 §2). The guest did not start, or either value differs: **Unattestable**, and the launcher makes no
   grant. *Contested* is unreachable at rung 1, as ADR-0034 §7 checked; the launcher has no measurement to
   compare with.
3. **Grant.** Request the lease over the operator channel with `confinement: [profile digest, 1]`, the Persona
   digest, the seat, round and role, and an alphabet without `Invoke`. The node returns the session token.
4. **Bridge.** For every line the guest writes on stdout, an `AgentOp` without a token, the launcher attaches the
   token and forwards it to the node's agent socket; every response goes back on the guest's stdin. When the guest
   closes stdout, or the round's terminal action is admitted, the launcher ends the round and the guest is
   destroyed.

**The token never enters the guest.** That is the session binding ADR-0034 §3.5 asks for at rung 1: the session is
the pipe, the pipe belongs to one launched instance, and no other process can use the lease, because no other
process holds the token. It replaces nothing in the node. I14's bearer token is still minted and still checked;
the launcher is the only holder. At rungs 2 and 3 the attested session key replaces this, as ADR-0034 §3.5 says.

**Every failure subtracts.** An unattestable launch makes no grant. A guest that dies closes the pipe, and the
launcher ends the round, an ordered subtraction attributed under F2. A launcher that dies takes the token with it;
the lease expires on its TTL (ADR-0031 §7) and the guest, with no reader on its stdout, blocks and is destroyed at
round end. Nothing in this list adds authority, which is the delegation test ADR-0034 applied to the host.

**Renewal re-attests the same instance** (ADR-0034 §3.6, ADR-0031 A1). The launcher renews only while the guest it
launched is still the process on the other end of the pipe. There is nothing to re-measure at rung 1, so the
re-attestation is the launcher's assertion again, and a renewal never changes the rung.

**Stderr is a second channel, outward.** The guest's stderr reaches the launcher's log and nothing else. It carries
no protocol and the guest reads nothing from it. It is named here so that P1's "one channel" is read as one
channel *for actions*, and it is listed in the profile.

### 3. The occupant is a scripted round with the Persona inside

The guest's process is an **occupant**: a fixed script that plays one Build round through the front door and uses
the Persona for the content of what it drafts. Its alphabet is `Read`, `Draft`, `Emit`, `Submit`. It never
`Invoke`s, so D-0034-3 does not arise and P4 is vacuous for it.

This is the shape the corpus expects. ADR-0022 §1 types what a principal *does*, not what it thinks; ADR-0016 §2
makes the Persona's suitability nobody's theorem; the occupant is Byzantine by premise, and at 1–50M parameters it
cannot follow an instruction anyway. What matters is that everything the guest does reaches the world through
`AgentOp` lines on one pipe, and that the weights that produce the drafted text are inside the guest and named in
the lease. The first satisfies ADR-0022 §6's obligation *for this guest*, up to the clauses §4 declares failed; the
second is P5 and the in-house conjunct of ADR-0034 §4.

**`Read` delivers content into the guest over the channel.** The guest mounts no corpus root; a `Read` is admitted
node-side and its content comes back on stdin. Ingress into the guest is therefore exactly the admitted `Read`s,
which is what ADR-0035 §1's `consumed` set records.

### 4. The first profile, declared

The profile for `slm/serve/`'s image, as this record's design has it. The ratification run (§7) writes the file
and its digest; the clause verdicts below are what the record commits to, and a run that finds otherwise is a
finding against this table, not a reason to edit it silently.

| Clause | Verdict | Why |
|---|---|---|
| **P1** one channel | pass | `--network none`; stdio is the only I/O the launcher connects. Stderr is outward-only and listed |
| **P2** filesystem | pass | Read-only root, a 16 MB non-executable tmpfs, and the three bundle files read-only. **Nothing else is mounted**, not even the workspace: the workspace lives node-side and the guest reaches it only through `Draft` and `Read` |
| **P3** no launcher for the principal | **fail** | The image carries a Python interpreter, which the occupant is written in, and the base image's `/bin/sh`. The Persona cannot cause either to run anything, because its output only ever becomes `Draft` content; but the clause is about what is reachable, and both are |
| **P4** tools are Wasm components | vacuous | The occupant's alphabet has no `Invoke` |
| **P5** inference is inside | pass | Weights and tokenizer are in the guest, digest-checked against `model.json` at start, and `model.json`'s digest is a reference value the launcher appraises |
| **P6** one principal per guest, one guest per round | pass | `--rm`; one launch per grant; the guest is destroyed at round end |
| **P7** the profile carries its reference values | pass | The image digest and the `model.json` digest. Changing either is a new profile |

**Subtractions to a passing P3:** an image with no shell and no interpreter reachable from the occupant. That is
either a compiled occupant on a `scratch` base, or an interpreter that is the occupant's runtime and nothing
else's, which is a question for the hermetic-shell record ADR-0034's Options names. It is the only item on the
list. Everything else in ADR-0034 §4 except the criterion holds for this guest.

### 5. What the launcher trusts, named

ADR-0034 §6 says rung 1 adds the host operator and orchestrator to the trusted base. For this launcher those are:

| Trusted for guest integrity at rung 1 | Why |
|---|---|
| The person who runs the launcher | Holds the operator socket, which is the grant authority in the reference (`mechanism/` G5) |
| The launcher script | Applies the profile's constraints, appraises, and holds the token |
| The container runtime and its daemon | Enforce the constraints the launcher asked for |
| On Docker Desktop, the Linux VM | The boundary between the container and the host |
| The image, by digest | What runs |

These are D-0034-2's type changes made concrete, and they are owed to the TCB declaration record (G3 item 16).

### 6. The launcher inside the node

This record's launcher is a script beside the rehearsal, holding the operator socket. That is the honest place for
it today, and it is the wrong place to stop. **The second step moves the four operations of §2 into `topak-node`
as a `launch` operator request**: the node starts the guest, appraises, grants to itself and bridges, and the
operator's role shrinks to asking for a launch. Three things change:

- **The attester becomes the mechanism** rather than a script the operator runs. At rung 1 that is still an
  assertion, but it is the mechanism's assertion, recorded in the grant entry with the profile digest and the
  instance it launched, as ADR-0034 §3.2 lays out for rungs 2 and 3.
- **The profile becomes a promoted artifact** (ADR-0034 §1, ADR-0024). A digest nobody promoted is not a reference
  value, and the node refuses to launch one.
- **The change is under `mechanism/`**, so ADR-0033 takes an addendum, its manifest moves, and every test in the
  suite runs again. `check_renewal` and the grant path do not change; what is added is a launch path that produces
  the grant request the operator produces today.

It is a separate step because it is a mechanism change, and this record's step is not. Rung 2 is not on this path:
a container has no launch measurement, and rung 2 needs a guest that boots, which is Firecracker or Kata, not
Docker. That is the rung-2 record's problem, and it will need the profile schema of §1 unchanged and a different
`launch` part.

### 7. Ratification condition

- The profile file for `slm/serve/`'s image exists, with every clause of §4 declared as the table says, and its
  digest is recorded in the run.
- One honest round: the launcher appraises Attested, grants at `[profile digest, 1]` with no `Invoke`, bridges a
  `Read` → `Draft` → `Submit` round in which the drafted content is the Persona's output, and the round ends with
  the guest destroyed. The transcript shows every `AgentOp` admitted, and the lease reports `contained = false`.
- **Three refusals, each seen to fire:** the image digest differs from the profile (Unattestable, no grant); the
  bundle inside the guest does not match `model.json` (the guest exits before its first line, no grant); a second
  process attempts the agent socket with no token (refused, the pipe is the only holder).
- A rung-0 principal run beside the rung-1 one, so that the two verdicts differ in the lease and in the profile,
  and `Mediated` at rung 1 is seen to be derived from P3 rather than from the rung.
- Results captured to a dated file under `slm/`, as the other rehearsals are.

### 8. Degeneracy on this record

| Id | Parameter → deployed value | Premises falsified | Theorems voided | Type changes (§6b) |
|---|---|---|---|---|
| **D-0036-1** | Profile has an interpreter reachable from the principal | P3 | Every `Contained` theorem, for principals under that profile | Those principals are `Mediated` (ADR-0034 §4). No participant changes type |

D-0034-2 (rung 1) is inherited and not restated. D-0036-1 is the same kind of entry as D-0034-3, for P3 instead of
P4.

## Options considered

| Option | Disposition |
|---|---|
| **Register `slm/serve` as a back-door tool** and leave the principals at rung 0 | Not taken as the step. Admissible, and cheap, but it advances nothing: the principal that `Invoke`s a native tool is `Mediated` by D-0034-3, and the model's role stays the wrong one |
| Mount the agent socket into the guest and run `topak mcp` inside | Rejected. Docker Desktop cannot carry a Unix socket into a container, and where it can, the token would be inside the guest, which is the binding ADR-0034 §3.5 says rung 1 must not rely on |
| A TCP loopback channel | Rejected. P1 has no network device, and `--network none` is the clause's realization |
| Put the launcher in `topak-node` now | Not taken first (§6). A `mechanism/` change needs an ADR-0033 addendum and a full rerun; the script gets the binding and the profile right before the node inherits them |
| Claim `Contained` for the rung-1 principal | Rejected. ADR-0034 §4 (R2) requires the criterion in force, and P3 fails in any case |
| Declare P3 `pass` on the ground that the Persona cannot invoke the interpreter | Rejected. The clause is about reachability. Reading it as intent would let every image with a shell pass |
| Mount the round's workspace into the guest read-write | Rejected. The guest does not need it: `Draft` and `Read` are node-side. Not mounting it is what makes P2 pass and keeps the guest's ingress equal to its admitted `Read`s |
| Give the occupant `Invoke` of `slm_pretrain`, so the rehearsal's training rounds run under the launcher | Not taken here. The trainer runs in the node's toolhost, not in the guest, so the round would not be ingress-bounded in ADR-0035's sense (finding 1) |

## Consequences

**Positive**
- **A lease at rung 1 exists in the reference**, issued on a profile with a digest, to a principal whose weights are
  inside a guest the launcher started. G1 stops reading "nothing".
- **`Mediated` becomes a derived verdict.** For this principal it follows from a declared P3 failure, and a test can
  show the derivation.
- **The session binding is by construction**, not by secrecy: the token has one holder and it is not the guest.
- **The subtraction list to a `Contained`-shaped guest is one item** (§4), and it is a build task, not a design
  question.
- **ADR-0035 gets a guest** whose `consumed` set is exactly its admitted `Read`s.

**Negative**
- **Nothing is `Contained`.** Not by this record, and not until ADR-0035 is in force and P3 passes.
- **The launcher is a script the operator runs.** At rung 1 the operator is in the trusted base anyway (ADR-0034
  §6), but a script beside a rehearsal is a weaker thing than a mechanism path, and §6 is owed.
- **Docker is not a VM boundary on Linux.** On Docker Desktop the VM is; on a Linux host the container shares the
  kernel, and gVisor (`SLM_RUNTIME=runsc`) is the nearest substitute. The profile's `launch` part must say which.
- **The occupant is a script, not an agent.** The round it plays is fixed; the Persona only supplies text. That is
  enough for the cage and says nothing about capability, as ADR-0035 §8 says of the rehearsal.
- **One author again.** Designed, built and, if ratified, ratified by one person; ADR-0034's caveat applies.

## Findings

1. **ADR-0035 R1 assumes tools run inside the guest.** Its ingress-bounded round says "a native tool (P4) or a shell
   (P3) inside such a guest reads only what the guest mounts." In the reference, `Invoke` runs the tool in the
   node's toolhost, outside any guest, with the workspace as its working directory (`mechanism/` G4). A training
   round under this launcher therefore has an ingress-bounded *occupant* and an unbounded *trainer*, and its
   lineage stays declared. Routed to ADR-0035: either the trainer runs in the guest, or R1 says the bound covers
   the occupant's reads and not the tool's.
2. **The host decides the channel.** Docker Desktop's inability to share a Unix socket is what made stdio the one
   channel, and stdio with a host-side bridge turned out to be the corpus's rung-1 shape. On a Linux host the
   socket could be mounted and the same design should still refuse to, for the binding's sake (Options).
3. **P1 needs a word about stderr.** "One channel" is one channel for actions. Every guest has a stderr, and this
   one's reaches only the launcher's log. The profile schema lists it so the clause is not read as violated.
4. **`slm/serve`'s README describes a tool, and the image is fit for an occupant.** Its sandbox flags are most of
   P1, P2 and P6 already. The role, not the container, was the gap.
