# ADR-0044 — A bundle is trusted by its signature, not its file name: the bundle key lives in the issued rules

## Context

The corpus is pinned to 40 digests in `mechanism/corpus-pins.sha256` and verified by manifest at every checkpoint.
The bundle the mechanism runs is not: `topak-bundle` reads a tarball's revision from its own manifest and trusts it
if the file name matches (I3, G7). A swapped tarball whose manifest names the expected revision is loaded; a sidecar
serving a forged bundle is trusted by its reported revision. ADR-0030 §2 wrote "Signed" into the bundle tier's
obligation and left the key unnamed. The 09.25 review graded the asymmetry (CR-24): record integrity best in class,
runtime artifact integrity open.

ADR-0034 §2 met the same shape for the verifier: a key that decides what the mechanism admits on the strength of a
signature is authority-defining, so it is carried in the issued rules and replaced by issuance. This record copies
that shape for the bundle.

## Decision

### 1. The bundle key is issued

Rules carry a set of **bundle keys** (ADR-0025 §1 (f)). A bundle is *signed* when its signature over the bundle's
content revision (§2) verifies under a key in the rules in force at load. Issuing or replacing a bundle key is an
issuance, like every other authority-defining key. An empty set is a deployment whose bundle tier loads nothing,
which ADR-0030 §1 turns into a deny on every request the floor would otherwise permit.

### 2. Identity is the content revision, and the signature covers it

The bundle's identity stays the content revision I3 computes: SHA-256 over the sorted (path, bytes) of every
non-test `.rego` and `data.json`. The signature is over that revision under domain separation, as `Authentic`'s
signing bytes are (`authentic.rs`), and is shipped beside the bundle as `<revision>.sig` *(drafter's choice: the
mechanism's own Ed25519 signature, verified by the mechanism, rather than OPA's `.signatures.json`, which OPA
verifies with its own key set outside the rules; see Options)*.

### 3. The mechanism refuses an unsigned or mis-signed bundle

- `load_dir` loads a tarball only if a signature beside it verifies under a bundle key and names the revision the
  manifest names. A file name is no longer evidence of anything.
- A sidecar's decision counts only if the sidecar's reported revision is one the mechanism has verified a signature
  for. The mechanism does not trust the sidecar to have checked; it checks the revision against its own set of
  verified revisions, which is what ADR-0033 §5's "from the bundle revision the lease names" already requires.
- A lease's `bundle` field is unchanged: it names a revision. A grant naming a revision with no verified signature is
  refused, as a grant under superseded rules is (I6).

### 4. Signing happens at promotion

A bundle is a promoted Build artifact (ADR-0024 §1). The bundle key signs the revision that promotion admitted,
after the tally and never before it. Who holds the key is a custody declaration (ADR-0025 Annex), not decided here
*(drafter's choice: the same custody row as the verifier key)*.

## Options considered

| Option | Why not |
|---|---|
| OPA's bundle signatures (`.signatures.json`, a JWS over file digests) | Verified by OPA with keys configured on the sidecar, outside the rules; the local WASM fallback would need a second verifier. Acceptable as an *additional* check on the sidecar; not the mechanism's check |
| No signature: the mechanism checks the revision against a promotion entry in its own log | The stronger long-term shape, since a promoted bundle is already consensus-ordered; but promotion of bundles is not in the log today, and ADR-0030 §2 asks for a signature. Noted as the successor when ADR-0024's promotion entries carry artifact digests |
| The anchor signs bundles | Every bundle promotion would need anchor unanimity (A-0025); the anchor issues keys, it does not sign artifacts |

## Consequences

**Positive**
- **The named asymmetry closes.** The artifact the mechanism runs is trusted the way the corpus is: by a digest a
  key vouches for, not by a name.
- **One shape for every vouching key.** Verifier and bundle keys enter rules the same way and leave the same way.

**Negative**
- **A key to keep.** The bundle key is one more custody row, and losing it stops bundle promotion until an issuance
  replaces it.
- **The sidecar path gains a check, not a trust.** A sidecar still cannot be trusted to have verified anything; the
  mechanism keeps its own set.
