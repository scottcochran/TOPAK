## Decision

### 1. The tla-kit image is one of TOPAK's pins, by a published digest, in `TLA-KIT-PIN` ⟨K1⟩

- **The file** is the one `CONSUMERS.md` names: `TLA-KIT-PIN`, new in `tools/`. One line per field, `key value`,
  in the form of `tools/TLAPS-PIN` *(drafter's choice)*:
  - `release`, the tla-kit tag (`vMAJOR.MINOR.PATCH`);
  - `image`, the full digest, `ghcr.io/scottcochran/tla-kit@sha256:…`;
  - `commit`, the tla-kit commit the release was built from;
  - `jar_sha256` and `tlapm_sha256`, the digests that release's `PINS.json` gives for `/opt/tla/tla2tools.jar` and
    `/opt/tlaps/bin/tlapm`;
  - `pinned`, the date.

  For `v0.1.0` the values are:
  - `release v0.1.0`
  - `image ghcr.io/scottcochran/tla-kit@sha256:454328cd7464efcf8a27a063c51c10086e09571c462c73d085b4a249e44950c6`
  - `commit bfeecc8f0bf9ea9446488a03ebd92ccb574c421a`
  - `jar_sha256 936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`
  - `tlapm_sha256 6182df63c4513b09c31c8de12c37f8045ace9cab2517c017a2fa75f466685bb2`

  The two digests are the values `v0.1.0`'s `PINS.json` gives for the installed files.
- **Only a digest tla-kit's release workflow published is pinned**, as tla-kit ADR-0002 item 7 says of what is
  cited. A local build of the image is working output.
- **The provenance is checked, not assumed.** CI runs `gh attestation verify` on the pinned digest against
  `scottcochran/tla-kit` before any job uses the image *(drafter's choice)*. It passes on `v0.1.0`'s digest for both
  attestations, signed for tla-kit's `release.yml` at `refs/tags/v0.1.0`. Each is signed under
  GitHub's identity, not an issued key. Under ADR-0069 §10.1 it meets C-2 and not G-2.
- **`tools/check-pins.sh` gains two checks** *(drafter's choice)*. The jar digest in `tools/TLA-PIN` equals
  `jar_sha256`. After §5, the binary digest in `tools/TLAPS-PIN` equals `tlapm_sha256`. Until §5, the second is
  reported and does not fail, since the pins name different builds on purpose.
- **One pull request moves the pin**, with evidence that fits what the release changed. tla-kit's version number says
  which kind (tla-kit ADR-0014 item 2):
  - **MAJOR, a checker moved:** the move waits on a record, as §5 is for the prover;
  - **MINOR or PATCH:** `results` and `proofs` run green on the pull request, and no results file changes.
  - **Before tla-kit's 1.0** the number does not say it: "while they do, a checker move may take a MINOR" (tla-kit
    ADR-0014 item 2). Until then the pull request reads which pins moved from the release's `PINS.json` *(drafter's
    choice)*.
- **TOPAK decides its own moves** (tla-kit ADR-0005 item 5). tla-kit's weekly check reads the pin and its log in
  `CONSUMERS.md` records each change (tla-kit ADR-0014 item 6). That entry is made in tla-kit by its custodian. This
  repository sends nothing there.

### 2. The `tlc` job runs in the image

- `results.yml`'s `tlc` job runs in the pinned image (`container:` by digest), in place of `actions/setup-java`.
  `tools/check-results.sh` runs unchanged, and finds the jar through `TLA_JAR` (tla-kit ADR-0004 item 4: no adapter).
- The jar is the same bytes as before, so no results file should change. The first run on a pull request has to show
  0 differences for every module of the tier. The JRE becomes the image's pinned Temurin 25 build, where
  `setup-java` gave whichever 25 release was current.
- `tools/ci-plan.sh` adds `TLA-KIT-PIN` to the `tlc` suite's inputs.
- The `reference`, `lean` and `floor` jobs are not changed. Their tools are not in the image.

### 3. A `proofs` job reruns every proof module in the image, and refuses a count that differs

- **Which modules:** every `spec/*_proof.tla`, as `spec/proof-sync.sh` enumerates them, in one job *(drafter's
  choice; F-3's run took 539 s in all)*.
- **When:** `tools/ci-plan.sh` gains a `proofs` suite. Its inputs are `spec/*.tla`, `spec/proof-results.sh`,
  `tools/tlapm`, `tools/TLAPS-PIN` and `TLA-KIT-PIN`. It also runs on every manual dispatch.
- **Until §5, counts only.** Each module is proved under the image's prover with `TLAPM_UNPINNED=1` and `--cleanfp`.
  Its obligation count and its outcome are compared with the newest committed results file. No results file is
  written. The output is kept as a workflow artifact, labelled as working output that names a prover the results
  files do not.
- **After §5, regenerated and compared.** `spec/proof-results.sh` writes a fresh file for each module, which is
  compared with the committed one as `tlc` compares TLC's. A file that differs is kept for reading, and the
  committed file is regenerated by hand as a new dated file. CI never writes one (ADR-0069 §6 G-1).
- **Strict** *(drafter's choice; Q3)*. F-3 found every count equal, and ADR-0069 §10.2 makes strict a check that
  passes on `main` when it is built. If the first run on `main` does not pass, the job is ratcheted instead, and the
  findings are listed.
- **Not in this job:**
  - the certified runs (`spec/proof-cert.sh`) and the defect run's certified step, because the image has no cvc5 and
    no ethos (tla-kit Phase 6);
  - `spec/proof-scan.sh`, which takes about 16 minutes. It runs on manual dispatch only *(drafter's choice)*.
- **What a green job means.** It is a carrier's check under ADR-0069 §9 C-2: it refuses and never admits. T-0045-13
  stays excluded, and nothing here changes its class. The evidence is the committed results file and its digest, as
  before.
- **This reverses ADR-0069 §6 G-3 for this repository.** G-3 says a gate "that cannot be rerun from its pin is
  checked for being in step, not re-derived". Once this job exists, a proof is rerun. Until §5 it is rerun under
  another build than the pin. ADR-0069 is Proposed, so this is an R-revision owed (Annex A, item 1).

### 4. `tools/TLAPS-PIN` gains `binary_sha256`

- The pin file gains `binary_sha256` with the full digest. For `7824dab` that is
  `e150fb793fb285922801252ddf96a227b060be293c2604e87be23935ef371e93` (Context). The owed-digest comment is removed.
- `binary_sha256_16` stays, as the first 16 hex of `binary_sha256` *(drafter's choice)*. Three scripts read it:
  `tools/tlapm` (`3f392b5be2c9e85d`), `tools/install-tlaps.sh` (`4d2244176ab5329c`) and `spec/proof-sync.sh`
  (`467b102f59dcd4c6`). Changing them would change three files that work, to remove a key that does no harm.
- `tools/check-pins.sh` checks that the two fields agree.
- The skill's `setup_check.py --proofs` then reports TOPAK's prover as pinned, with no change to the skill.

### 5. The prover pin moves to the image's build by its own pull request, once five things are done *(drafter's recommendation; Q1)*

**The recommendation is to move**, for two reasons. The pinned build has both known unsound cases, and the image's
build carries upstream's fixes for the first and for the collision half of the second. And it is the only route by
which CI reruns the proofs under the pin. Ratifying this record decides that the move is made, and when. It does not
make the move.

Before the pull request that moves `tools/TLAPS-PIN`:

- **(a) The defect record is rerun under `ff40755`, in the image, and read.** Every listing of
  `spec/proof-certification.md` §8 is read for its outcome under every route: tlapm, the certified run and TLC. The
  run states, for each false statement, whether it still proves on any route, and for each true statement, whether it
  still proves. The capture listings (`CaptureName`, `CapturePTL`) are read separately, since #339 does not say it
  addresses a capture. `defects-run.sh` states its expectations of `7824dab`: "Both cases reproduce". A successor
  states its expectations for each build, so that a fixed case reads as the expected outcome and not as "DIFFERS". Its
  results are a new dated file. `spec/defects/defects-results-2026.10.22.txt` (`692d74d63b6bbec4`) stays the record
  of `7824dab`.
- **(b) Every proof module is regenerated in the image**, with `spec/proof-results.sh` (`5476b45862cf54b9`), as a new
  dated results file. The counts are compared with `7824dab`'s, and every difference is listed and explained.
- **(c) The certified configuration is rerun** with `spec/proof-cert.sh` (`315fa3d07b7a42de`), for every module with
  a certified results file. There are 34 such files in `spec/` (`*-proof-cert-results-*.txt`), against the eleven
  certified modules ADR-0046 A1 listed. Which of the 34 certify was not counted for this draft. Without this rerun,
  those modules' certified standing rests on `7824dab`'s files and not on the pin. The image has no cvc5 or ethos. **The recommendation is to wait for tla-kit to carry them**
  (Q2). Supplying them to the container from outside would put tools in the run that the image's digest does not
  name, which tla-kit ADR-0002 item 6 and ADR-0004 item 4 are written to prevent.
- **(d) `spec/proof-scan.sh` (`9da631cea50b3807`) is rerun under `ff40755`, and read.** Whether the scan is still
  needed after #339 is for ADR-0046 to say, by amendment. This record does not retire it.
- **(e) The records that cite the two cases are read**: ADR-0037, ADR-0045, ADR-0046, ADR-0053 and ADR-0069, and
  `spec/proof-certification.md` §8 and §10. Their dependent entries are drafted (Annex A, items 2 and 3).

**The move itself**, in one pull request:
- `tools/TLAPS-PIN` names `ff40755`, x86_64-linux, the image's `tlapm_sha256` as `binary_sha256`, its first 16 hex as
  `binary_sha256_16`, and the backends `tla-kit-info` prints. It gains `image`, naming `TLA-KIT-PIN`.
- The results files of (a) and (b) are committed. The `proofs` job switches to regenerate and compare.
- **The results files that name `7824dab` stay results of `7824dab`** (ADR-0046 A3). The records that cite them by
  digest keep citing them *(drafter's choice)*. A record moves its citation to a new file by its own amendment.
- **Proof runs on the custodian's machine go through the image**: under emulation on Apple Silicon, which tla-kit
  measured twice for the full run on 12 CPUs: 6 min 43 s on a local build, and 417 s from the published image.
  A new script in `tools/`, `tla-kit` *(drafter's choice)*, runs a command in the pinned image with the repository
  mounted at `/work`. The darwin install that `tools/install-tlaps.sh` makes is then not the pinned prover, and
  `tools/tlapm` refuses it without `TLAPM_UNPINNED=1`, as it should.

### 6. Two corrections the session listed are made with §4

- `spec/defects/defects-run.sh` says plainly when its certified step cannot run, where today it prints empty counts
  (session record §9 item 5).
- `tools/install-tlaps.sh` states the size of what it fetches as measured. The session measured the current x86_64
  tarball at 52 MB, where the script says "1.1 GB compressed, 1.9 GB on disk" (F-6). The darwin tarball was not
  measured, so this record does not say which figure is wrong.

### 7. Ratification condition

- **tla-kit has published an attested release.** **Met** on 2026.11.16: `v0.1.0`, `sha256:454328cd…50c6`, whose
  attestations verify. tla-kit's repository is public, and its kept prover release `tlapm-ff40755` exists.
- **`TLA-KIT-PIN` names that release by digest, and `tools/check-pins.sh` checks it** (§1). **Not met.**
- **`tlc` runs in the image on a pull request, with 0 differences on every module of the `pr` tier** (§2). **Not
  met.** F-4 found 0 differences once, in tla-kit's spike, not in CI.
- **`proofs` runs on a pull request and passes, counts only** (§3). This is tla-kit's "Done when" for Phase 2. **Not
  met.**
- **`tools/TLAPS-PIN` carries `binary_sha256`, and the skill's setup check reports the prover pinned** (§4). **Not
  met.** The value is measured (Context). The file is not changed.
- **§6's two corrections.** **Not met.**
- **The dependent entries in Annex A are drafted**, and the pins of the records they touch are moved. **Not met.**
- **A reader who is not the drafter** (ADR-0029 A2). **Not met.**
- **The custodian's reading of every drafter's choice and recommendation**, Q1 to Q3 among them. **Not met.**

**No module is asked for** *(drafter's choice)*. This record moves where tools run and adds checks that refuse. It
states no property of the mechanism. `tla-kit:spec/PinLifecycle.tla` models the pin process on tla-kit's side, not
TOPAK's.

**§5 is not a condition of this record.** Its five steps are conditions of the move. This record can be ratified with
the pin still on `7824dab`.

## Consequences

**Positive**
- Every pull request that touches a proof module reruns it. Before, CI only checked that results files named the
  pinned prover and matched their modules' digests.
- TLC runs on a pinned JRE as well as a pinned jar.
- After §5, the prover TOPAK cites is one whose tarball is kept and whose digest is published and attested, and
  which upstream has fixed for the first case and for collisions. ADR-0046's open obligation on the prover's install
  is answered.
- The skill's scripts recognise TOPAK's prover pin.

**Negative**
- TOPAK's CI depends on a registry and on a repository with one custodian. If tla-kit stops publishing, the pinned
  digest still resolves (tla-kit ADR-0014 item 5), but no new one comes.
- Until §5, `proofs` reruns under a build the results files do not name. A pass corroborates and does not
  regenerate. A failure may be the newer prover's and not the proof's, and has to be read as such.
- After §5, proving on the custodian's machine runs under emulation, and needs Docker.
- After §5, the corpus cites two prover builds: `7824dab` in the files the accepted records cite, and `ff40755` in
  every file after. A reader has to tell which a citation is on.
- The defect record has a successor and two expectations, one per build.
