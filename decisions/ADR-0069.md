## Context

**Every step a Build artifact takes on its way to Run is decided somewhere, and the path that joins them is not.**
The steps are spread across many records:
- ADR-0024: everything crossing from Build to Run is promoted, by a unanimous quorum, with the author recused and the
  votes in the log.
- ADR-0021: a Build round is one pipeline invocation, sealed at submission, and every vote covers provenance.
- ADR-0044 §4: the bundle key signs after the tally and never before.
- ADR-0031: a new bundle reaches a live principal by ending its round.

ADR-0033 says what is missing: "The reference has never been promoted, and no promotion pipeline exists to promote
it." Its addendum A6 lists, as not discharged, "signing at promotion as a step of a promotion pipeline, which does
not exist (ADR-0044 §4 is a script with a secret)."

**The custodian asked for that pipeline as one record**, restating or reversing every earlier Build decision ⟨K1⟩.
It is to be generic in what it requires and specific about git and GitHub ⟨K2⟩, and it is to repurpose the CI/CD
already working in the f1-tla repository ⟨K3⟩. The custodian then asked whether the pipeline is Build-Run-Build:
whether it includes retraining on experience and taking training data from Run ⟨K4⟩.

**It does, and the notation stays.** ADR-0001 made the arrow in `Build(Contain) → Run(Contain)` mean authority flow.
A Run→Build arrow would say that Run grants Build authority, and no record allows that. What comes back from Run is
data. It enters Build as ingress, and it has force only after a round reads it and the round's artifact is promoted.
So the pipeline has a **return path** and no return arrow. The return path enters at the one place where anything
enters Build: the corpus root.

**The corpus root has no admission rule.** ADR-0022 §3 makes the corpus root "a pinned, content-addressed set" and
scopes `Read` to it. It does not say how an object comes to be in it. ADR-0041 lists "What may enter the Run root, and
who admits it. Build's corpus root has the same question open." ADR-0054 (Proposed) says "Build has a path, promotion
into the corpus root, and it is a quorum per artifact." ADR-0035 (Proposed) records `generatedBy` as "declared at
admission" for external objects. Three records point at an admission step, and none defines it. The custodian
settled that intake from Run is a case of intake in general ⟨K5⟩, and that a labelled return is a separate case
⟨K6⟩.

**What exists to repurpose.** f1-tla runs three GitHub Actions workflows. Each is thin YAML that calls a repository
script, and the scripts run the same way by hand:
- `checks`, on every push and pull request: the TLC jar against its pin, the proofs against the specifications (no
  prover needed), and the incidents.
- `results`, when the specifications or the tools change: it regenerates every TLC results file and compares it with
  the committed one, and it never writes to the tree.
- `sources`, on demand only: it checks the pinned upstream documents, and it reports without editing.

Its `check-proofs.sh` is adapted from TOPAK's own `spec/proof-sync.sh`. TOPAK has no workflow today. Its `main`
branch has no protection, and its `CODEOWNERS` names one person.

## Decision

### 1. The pipeline is one ordered path, keyed by digest ⟨K1⟩

**Every artifact that crosses from Build to Run travels the stages below, in order, and each stage takes only the
digest the stage before it produced.** ADR-0024 §7 already calls a promotion "a pipeline invocation of the promotion
stage, keyed by artifact digest". This record makes the rest of the path part of that one object.

| Stage | Takes | Produces | Decided by | New here |
|---|---|---|---|---|
| **0. Intake** | Objects with their sources | A corpus-root revision, promoted | — | **§3, ~~§4, §5~~ *§3a (its gates), §4, §5* ⟨R1⟩** |
| **1. Round** | A corpus-root revision, a seating, a tool list | Leases at a fresh fence | ADR-0022 §2, §3; ADR-0024 A3; ADR-0048 | — |
| **2. Author** | `Read`, `Draft`, `Invoke`, `Emit` | A workspace, round topics | ADR-0022 §1; ADR-0034 P1–P7; ADR-0021 §1 | — |
| **3. Submit and seal** | The workspace | The artifact digest; the sealed topic-set digest | ADR-0022 §1; ADR-0021 §3; ADR-0044 §2 | — |
| **4. Gates** | The artifact digest | Gate evidence and its digest | ADR-0024 §4; ADR-0007; ADR-0010; ADR-0030 §5; ADR-0016; ADR-0023 §7b | **§6**: who signs the evidence*, and which gates each class has (G-4)* ⟨R1⟩ |
| **5. Tally** | (artifact, evidence, epoch) | The promotion entry in the log | ADR-0024 §2, §3, §6, §8; ADR-0021 §4; ADR-0039 §3 | — |
| **6. Sign** | The promotion entry | A signature over the artifact digest | ADR-0044 §4 | **§7**: every class, and its separation |
| **7. Publish** | The artifact and its signature | A content-addressed copy | ADR-0044 §3 | **§8** |
| **8. Roll out** | A promoted, signed revision | Leases naming it | ADR-0031; ADR-0024 §9 | — |

**Requirements on the path:**
- **P-1. No stage starts on a name.** It starts on a digest, and refuses one the stage before it did not produce.
  This is ADR-0044's "A file name is no longer evidence of anything", applied to every stage *(drafter's choice)*.
- **P-2. A stage's output is either a log fact or an object signed under an issued key.** It is never a carrier's
  record of a step (§9).
- **P-3. The stages are not reordered.** Gates run before the tally (ADR-0024 §4), and signing comes after the tally
  (ADR-0044 §4). Publication follows signing, and rollout follows publication.
- **P-4. An artifact that stops at any stage has no egress.** ADR-0039 §3 already holds this for an unsubmitted round:
  "An authoring round that is never submitted has no egress".

The table restates. The new decisions are stage 0 and the rules for stages 4, 6 and 7. Annex A disposes of every
earlier Build decision clause by clause.

### 2. Authority runs one way; what Run produces returns as data and enables nothing ⟨K4⟩ ⟨K7⟩

**The notation is ADR-0002's, unchanged: `Build(Contain) → Run(Contain)`, with the arrow as authority flow
(ADR-0001).** This record adds no arrow.

**Restated: Run does not adapt** ⟨K7⟩. Five accepted clauses settle this:
- ADR-0015 defines "Authority changes: exactly {promotion, anchor issuance}".
- ADR-0024 §1: "Any artifact crossing from `Build` to `Run` requires promotion."
- ADR-0034 P5 makes a Persona's weights part of the launch measurement.
- ADR-0034 P7 makes a change to either reference value "a new profile, and so a promotion".
- ADR-0034 P6 says "Nothing survives except through `Submit` and `Emit`", and the Run profile carries it over
  (ADR-0034 A2).

Together they mean that weights, a bundle, a profile or a seating that changed in Run would be one nobody promoted.
The next attestation does not match it, and the mechanism refuses the lease. **Learning from Run happens in a Build
round, on data that intake admitted, and reaches Run only by promotion.**

**The return path** ⟨K4⟩. What Run produced enters Build only as an object admitted to a corpus root by intake (§4,
§5). It enables nothing until a round reads it and the round's artifact passes stages 3 to 8. Every lap of the loop
passes the promotion gate, so the loop adds no path for authority. What it adds is a path for influence, and §4 and
§5 bound that.

### 3. Intake is the only way into a corpus root ⟨K5⟩

**A corpus-root revision is a Build artifact, promoted under ADR-0024 like any other.** Its content is a manifest
with one line per object. Nothing else changes what a round may `Read`. This answers the Build half of ADR-0041's
open obligation. It agrees with ADR-0054's sentence on the corpus root, which is Proposed.

*(Drafter's choice: intake is a promotion. The alternative, an operator's attributed act, is in Options. It was not
taken because a corpus root decides the ingress of every round that pins it, and so the lineage of everything those
rounds produce. ADR-0022 §3 calls the root "the syntactic control over ingress".)*

Each manifest line names:

| Field | Content |
|---|---|
| `digest` | SHA-256 of the object's bytes. The object's identity, as ADR-0044 §2's revision is a bundle's |
| `source` | One of `external` (with the upstream identifier and the digest it was pinned at), `promoted` (with the promotion entry), or `run` (§4, §5) |
| `generatedBy`, `curatedBy` | The declaration ADR-0035 §1 says is made "at corpus admission", or the projection §4 requires for `run` |
| `label` | Empty, except under §5 |

**Requirements on intake:**
- **I-1. An object with no source line is not admitted**, and a revision that drops a line drops the object.
- **I-2. An external source is pinned by digest at admission.** A check that an upstream source is still served at its
  pin, and that no newer issue exists, reports and never edits. A finding against a pin is input to a new intake.
  This is f1-tla's `sources` workflow.
- **I-3. Intake does not judge content.** Restated from ADR-0022 §3: "Whether the corpus is *poisoned* is an Observer
  finding, not an enforcement decision". The intake round's Observer and the veto seats deny on it (ADR-0024 §5).
  ~~The gates check only the manifest's form.~~ *The gates of §3a check the manifest's form and recompute what can be
  recomputed. None of them reads an object for its meaning, and §3a says what that leaves unchecked* ⟨R1⟩.
- **I-4. A cognitive payload (ADR-0004) is admitted only under §5.**
- **I-5. A revision is classified against the one in force, by set difference on digests:** additions, removals, or
  both. An addition widens what a round may read, so it is the intake counterpart of a relaxation. It promotes as any
  artifact does, and its `generatedBy` lines feed ADR-0035's exclusion rule, which is monotone in them *(drafter's
  choice)*.

**The Run root is not decided here.** ADR-0041 asked about the Run root as well. A Run root crosses from Build to Run,
so ADR-0024 §1 already requires it to be promoted. Whether this section's manifest form is its form too is left open
(Open obligations).

### 3a. What gates an intake ⟨R1⟩

**The vote on an intake opens only when all seven gates below have passed, and each has written evidence that is
signed under §6 G-2,** or, while D-0069-2 holds, attributed by `AttestGates` (ADR-0050). They are mechanical, because ADR-0007 bars semantic judgment as an enabling condition. Each is a
program named by digest (§6 G-1). The author of an intake is the principal that submits the manifest, and that
principal is recused (ADR-0024 §6).

ADR-0024 §4's two checks are ADR-0007's gates and `bundle ⊑ floor`. Both are written for policy artifacts, and on a
manifest they would pass on nothing. §6 G-4 says what replaces them for this class.

| Gate | Passes when | Enforces |
|---|---|---|
| **IG-1 Resolve** | Every digest in the manifest is in the store, and the stored bytes hash to it | §3 identity |
| **IG-2 Complete** | Every object the revision admits has exactly one line, and every line has a `source` and its `generatedBy` and `curatedBy` fields | I-1 |
| **IG-3 Pinned** | Every `external` line has an upstream identifier and the digest it was pinned at. Where the upstream still serves the object, the runner fetches it and the bytes match. Where it does not, the evidence says so and the line stands on its declaration *(drafter's choice)* | I-2 |
| **IG-4 Recompute** | For every `source: run` object, the allowlisted extractor named by digest is rerun on the cited log positions, and its output has the object's digest. The `generatedBy` shares are recomputed from the same positions and match | §4 RR-1. Without this gate, "computed, never written" would be a claim the submitter makes |
| **IG-5 No payload** | No `run` object takes input from an entry in the governed store (ADR-0004) or from a labelled item. While §5 LR-1 is unmet, no labelled object passes | I-4, §5 LR-1 |
| **IG-6 Labels grow** | Every object's label contains its label in Run. While IG-5 admits no labelled object, this gate is vacuous, and its evidence says so | §5 LR-2 |
| **IG-7 Classify** | The additions and removals against the root in force are computed and written, with the lineages whose `generatedBy` shares change. The gate always passes once its report exists. At tally, an intake classified against a root that is no longer in force is refused and gated again *(drafter's choice)* | I-5; the grant seats' evidence |

**IG-7's tally check keeps two intakes from racing.** Each was classified against the root that was in force when it
was gated. If one promotes, the other's report is stale, and the voters would be voting on a difference that no
longer exists.

**What no gate checks: poisoning.** I-3 leaves the content to the veto seats. Here is what that amounts to:
- **The Observer's coverage duty is to the seal of the intake round's topics** (ADR-0039 §3). The corpus objects are
  in those topics only as far as the round read them. A veto seat denies only on what it samples.
- **The grant seats vote on IG-7's report**, not on the data.
- **The first check of what the data does is Persona verification**, at the promotion of a Persona trained on it
  (ADR-0016). That is after the intake, and after the training.

So for a corpus of any size, intake checks where data came from and that it is what it claims to be. It does not
check what the data will teach. This is a declared residual, in the same place ADR-0022 §3 put it, and nothing here
narrows it.

### 4. Intake from Run is a case of intake ⟨K5⟩

**An object with `source: run` is computed from the log by an allowlisted tool in a Build round, never written by a
principal.** This is ADR-0035 §1's rule for lineage, "projected from the log, not authored", applied to data. The
extraction round is an ordinary Build round, and its artifact is the objects together with the log positions they
derive from.

**What may return without a label** ⟨K6⟩ is a control-plane fact (ADR-0004), or a record derived only from control-plane
facts:
- admit decisions (ADR-0028 F1);
- stop attributions (F2), which ADR-0028 calls "a feedback path, not merely evidence";
- promotion votes (F3);
- `Actuate` records, by digest (ADR-0042 §3, §4);
- Observer and correlator findings.

None of these is erasable, so their return carries no erasure obligation. Everything else a Run round holds is a
cognitive payload or a labelled item of ingress (ADR-0047 §1), and returns only under §5.

**Requirements on a return from Run:**
- **RR-1. `generatedBy` is projected, not declared.** It names the Personas whose principals' admits produced the
  source entries, each with its share. This gives ADR-0035's field a source in Run. That record says of its rule that "It
  applies to no lineage node today", because every node is a Build round.
- **RR-2. A return is charged to every lineage named in its `generatedBy`.** A successor trained on a cell's record
  has the cell's Thinker and its Observer both in its lineage. ADR-0035 §3's exclusion rule then decides what
  independence that successor can claim. A deployment that wants two lineages to stay independent admits each
  lineage's own record to that lineage's corpus root, and not the other's *(drafter's recommendation; ADR-0017
  requires "two independent lineages" at the archetype)*.
- **RR-3. Each object lists the findings recorded against its source rounds**, so that the intake's veto seats read
  them. A finding subtracts, as ADR-0007 requires. It is never a precondition, and its absence is never a grant
  *(drafter's choice)*.
- **RR-4. Retention.** The source entries keep their own horizon. The returned object is retained as a corpus object:
  for the production lifetime of any artifact promoted from a round that read it (ADR-0021 §7). This lengthens the
  life of the derived object and never that of the source topic (ADR-0003 A3).

**What this does not bound** ⟨K4⟩. A Byzantine Run principal can shape the record its successor trains on: within
its alphabet, it chooses what to `Consult` and what to `Actuate`. RR-1 and RR-3 make that influence visible and
attributable. Nothing in them makes it harmless. The behavior of the trained successor is checked only by Persona
verification, which ADR-0016 added as "a required Build gate". That is the residual. ADR-0017's remark that
"Thompson applies to the trainer" now applies to Run as one of the trainer's sources.

### 5. Labelled return is a separate case, and admits nothing until Build labels ⟨K6⟩

**A labelled return** is a Run item that carries an ADR-0047 label, or a cognitive payload: the task, the content of
a `Consult`, the result of an `Actuate`, a principal's emission. **It is admitted only when three conditions hold:**

- **LR-1. Build's Listener labels.** ADR-0047 §9 leaves it open: "Whether Build's Listener labels is not decided
  here." A labelled item read by an unlabelled Build round loses its label at the point it matters. An `untrusted`
  item would reach a Build Thinker in the clear, with nothing to mark it. **Until a record decides that Build labels,
  no labelled return is admitted** *(drafter's choice)*.
- **LR-2. The label travels, and only grows.** An object's label in the corpus root contains its label in Run. An
  intake may add a name and never remove one *(drafter's choice; the monotone direction ADR-0035 §2 takes for
  `ingress`)*.
- **LR-3. Erasure follows the data.** Each object names its erasure locus: the sealed topic, or the entry in the
  governed store (ADR-0004), that it came from. An erasure of that locus (ADR-0006) obliges two things:
  - a new intake revision without the object;
  - for every promoted artifact whose lineage `ingress` contains it, withdrawal or a declaration. Withdrawal means
    ending the rounds that name it (ADR-0031) and refusing grants that name it.

  The obligation is keyed on `ingress`, which ADR-0035 §2 allows to over-approximate, and not on `consumed`, which
  must never over-approximate and so could miss an artifact *(drafter's choice)*. **This is a proof obligation over a
  privileged path, and the reason C1 attaches.**

**The forensic floor is untouched.** An erasure that removes a payload leaves its F-class facts (ADR-0028 §1). A
labelled return removes nothing from the log.

### 6. A gate is a program named by digest, and its evidence counts once an issued key signs it

**Restated:**
- `Vote` is enabled only after the gates pass (ADR-0024 §4). The gates are:
  - ADR-0007's totality, non-vacuity and discrimination gates;
  - `bundle ⊑ floor` (ADR-0010), with floor revisions classified mechanically (ADR-0030 §5);
  - Persona verification (ADR-0016);
  - the declaration check (ADR-0023 §7b).
- For a bundle, the gate "reduces to the three ADR-0007 gates plus signing" (ADR-0030).
- Gate evidence is recorded by an operator's `AttestGates` (ADR-0024 A3, ADR-0050). That records who asserted the
  evidence, not whether it is true.

**New:**
- **G-1. A gate is a program in the repository, named by digest, and it runs the same way by hand and on a carrier.**
  Its evidence is the file it writes. The digest of that file is ADR-0024 §3's gate-evidence digest. A results file
  is never edited by hand. A rerun that changes anything is a new file *(drafter's choice; f1-tla's rule)*.
- **G-2. Evidence counts as more than an assertion once a gate-evidence key, carried in the issued rules, signs it.**
  These are the terms ADR-0045 §6 already set for the gate runner, which it found "admissible as a trust root" with
  "its evidence signed by a key carried in issued rules, which ADR-0025 §1 (f) can now hold. Until that key exists,
  T-0045-13 is excluded". This record names the key. Issuing it is an amendment to ADR-0025 §1 (f) (Annex B, item
  5). Until the key is issued, T-0045-13 stays excluded and nothing here changes its class.
- **G-3. A gate that cannot be rerun from its pin is checked for being in step, not re-derived.** The pinned prover is
  tlapm `7824dab` (`tools/TLAPS-PIN`). Its upstream tag now serves another build, and its binary is pinned for
  arm64-darwin. No carrier can rerun the proofs with it unless the deployment hosts that binary. A carrier runs
  `spec/proof-sync.sh` and reports which proofs are stale. The proofs themselves are rerun where the pinned binary is.
- ⟨R1⟩ **G-4. A vote opens on its own class's gates, and a class with none stated does not promote** *(drafter's
  choice; the alternative is in Options)*. ADR-0024 §4 states two checks for every class. They fit bundles and floors,
  and say nothing about a manifest, a profile or a seating. A gate that says nothing about an artifact passes it, so
  the vote would open on nothing. The table below sets out each class's gates. A class whose row states none waits
  until a record writes them. Annex B, item 8, carries the change into ADR-0024 §4.

  | Class | Gates a record states | Where |
  |---|---|---|
  | Operational bundle | ADR-0007's three gates; `bundle ⊑ floor`; signed | ADR-0024 §4; ADR-0030, its bundle row |
  | Policy-floor revision | ADR-0030 §5's gates, and the computed classification | ADR-0030 §5; ADR-0010 A2 |
  | Rules-floor revision | ADR-0007's gates on the rules floor, with an issuance alongside | ADR-0026 §3, §4 |
  | Mechanism code | **None.** A reproducible build is T-0045-30, a debt | ADR-0045 |
  | Persona | Persona verification. The lineage is computed by the gate, and independence is checked in the tally | ADR-0016; ADR-0035 §1, §4 (Proposed); ADR-0024 A2 |
  | Confinement profile | **None.** ADR-0034 states what a profile fixes, not a gate that checks it | ADR-0034 §1 |
  | Seating | **None of its own.** ADR-0024 A3 records "the gates of §4" as run, and they do not read a seating | ADR-0024 A3 |
  | Deployment declaration | The composition note exists and states its delta. ADR-0058 adds the graph overlay (Proposed) | ADR-0023 §7b; ADR-0058 §8 |
  | Workflow | Not re-read for this revision. ADR-0054 is Proposed | ADR-0054 |
  | **Corpus-root revision** | **IG-1 to IG-7** | **§3a** |

  Mechanism code, profiles and seatings cannot promote under this record until a record gives them gates. During
  genesis, nothing promotes, so nothing waits yet.

### 7. The tally is the log's; signing follows it, for every promoted artifact

**Restated:**
- Unanimity over the grant seats; "A timeout is never a grant"; the round stalls without an independent veto seat
  and without coverage to the seal (ADR-0024 §2 and A2; ADR-0039 §3).
- A vote binds to the triple, and a change of epoch voids votes in flight (ADR-0024 §3).
- Author recusal is a mechanism constant (ADR-0024 §6).
- Votes are non-erasable, and "The authoritative vote is the admit decision in the consensus log" (ADR-0024 §8).
- Every vote covers the sealed topic set (ADR-0021 §4).

ADR-0024 §7 says promotion "does not depend on" ADR-0021, while A2 stalls on ADR-0021 §3's seal. The two clauses do
not conflict. §7 is about where the vote is recorded, and A2 is about when the tally may complete. No text needs to
change.

**Signing, widened to every class.** ADR-0044 §4 says "The bundle key signs the revision that promotion admitted,
after the tally and never before it." **Every artifact class promoted under ADR-0024 §1 is signed the same way**:
- bundles;
- mechanism releases;
- Personas;
- profiles;
- seatings;
- corpus-root revisions (§3);
- workflows, if ADR-0054 is ratified.

Each is signed under an issued key, after its tally *(drafter's choice; per-class keys are in Options)*. **This
reverses in effect ADR-0016 §1**, whose Persona ID is "Cryptographically signed by the Build promotion key". ADR-0002
A1 struck the single human key at Build's commit point, and ADR-0025 §1 (f) lists no such key. Annex B, items 1 and
4, carry the change.

**Separation:**
- **S-1. The signing stage holds the key and nothing else.** It recomputes the artifact digest from the bytes, reads
  the promotion entry for that digest from the log, and signs only if the entry is there. No author code and no gate
  runs where the key is reachable.
- **S-2. The signature is over the digest, under domain separation**, as ADR-0044 §2 has it.

ADR-0044 noted a stronger successor: no signature at all, with "the mechanism checks the revision against a
promotion entry in its own log". This record makes the promotion entry name the artifact digest. That successor is
possible after this record, and it is not taken here.

### 8. Publishing locates; rollout ends rounds

- **Publishing places the artifact and its signature where nodes can fetch them by digest.** The location is not
  evidence (P-1). A node verifies the signature under the keys in force (ADR-0044 §3) before it loads anything.
- **Restated: a new revision reaches a live principal by ending its round**, and across the fleet by an epoch fence
  (ADR-0031). Runtime subtraction is not promotion (ADR-0024 §9). "There is no emergency seat in Build; a promotion is
  Build's way to add authority" (ADR-0052).
- **Restated: the fast path for strictly subtractive bundles stays deferred** (ADR-0024, Options).

### 9. A carrier moves objects and decides nothing

**A carrier is every system that moves objects between stages or runs gates for an operator:** version control, CI
runners, artifact hosting. **This record does not make a carrier a trust root** *(drafter's recommendation)*.

- **C-1. A carrier's approval is not a vote, and its merge is not a promotion.** The facts that count are the log's
  (ADR-0024 §8) and the issued keys' (§6, §7).
- **C-2. A carrier's checks may refuse and never admit.** A branch rule or a required review is defence in depth.
  This is the standing ADR-0044's Options gave OPA's signatures: "Acceptable as an *additional* check".
- **C-3. A CI runner is not a principal** *(drafter's recommendation)*. It holds no Build alphabet. It runs gates on
  an operator's behalf, and the operator's `AttestGates` records the result (ADR-0050). The ADR-0022 §6 obligation
  ("no shell, no network egress… no path into the artifactory except `Submit`") binds Build principals, and a
  runner has all three. So a runner is in T-0045-13's row and counts only as G-2 allows.
- **C-4. Author code never runs where signing or gate-evidence keys are reachable** (S-1).
- **C-5. A carrier's identifiers locate and do not identify.** A commit hash, a tag or a release name points at an
  object. The SHA-256 in §3 and ADR-0044 §2 identifies it.

### 10. Git and GitHub ⟨K2⟩ ⟨K3⟩

**This section is guidance.** Under the adopter's-guide convention, its "should" is advice, and what it must do is
§1 to §9's. Each line maps a generic requirement onto git and GitHub, and says where GitHub stops.

#### 10.1 The mapping

| Generic | git and GitHub | Where it stops |
|---|---|---|
| Corpus-root revision (§3) | A manifest file in the repository, changed by pull request | **The objects are not in git**, only their digests. They go in a content-addressed store |
| Intake from Run (§4) | An extraction round whose artifact is a manifest change | The extractor is an allowlisted tool, not a workflow step |
| Labelled return (§5) | **Never in git.** Rewriting history to erase it would be the out-of-band deletion ADR-0006 forbids | — |
| Round (§1, stage 1) | A branch per round, in a worktree the mechanism owns | A Build principal does not run git (ADR-0022: "No shell, no package installation, no network, no git") |
| `Submit` and seal | The mechanism commits the workspace and opens a pull request naming the artifact digest and the sealed topic-set digest | The pull request is a locator (C-5) |
| Gates (§6) | Required status checks: workflows that call repository scripts | A check's green is the carrier's. The evidence file and its signature are what count (G-2) |
| Gate evidence | A workflow artifact, signed in a separate job under the gate-evidence key | GitHub's artifact attestations may be added. They are signed under GitHub's identity and not an issued key, so they meet C-2 and not G-2 |
| Tally (§7) | A required check, `tally`, that reads the log's promotion entry for the digest | Reviews, CODEOWNERS and required approvals are defence in depth (C-2). GitHub's ban on approving one's own pull request echoes recusal, which is a mechanism constant |
| Votes voided on change | "Dismiss stale approvals when new commits are pushed" | Covers a new artifact digest, not a new rules epoch. The `tally` check covers both |
| Sign (§7) | A job in a protected environment holding the key, triggered on the merged commit, which does only S-1 | Environment reviewers approve any-of. They are not a quorum |
| Publish (§8) | A release carrying the artifact and `<digest>.sig` | The tag locates (C-5) |
| Roll out (§8) | Outside GitHub. Nodes fetch by digest and verify | The epoch fence is the mechanism's |
| Upstream pins (I-2) | An on-demand workflow that reports and never edits | — |

**Should, throughout:**
- Workflows declare `permissions: contents: read` unless a job needs more.
- Third-party actions are pinned by commit SHA, not by tag. f1-tla pins by tag, and this is the one change to its
  workflows.
- A job that holds a key runs no repository code except S-1's.

#### 10.3 The corpus repository during genesis *(drafter's recommendation)*

TOPAK's own repository runs `checks`, `results` and `sources` as **gate evidence for the custodian's ratification
and for the reference. During genesis they promote nothing.**
- Genesis ratification is the custodian's (ADR-0029 §2).
- No roster exists until the ceremony seats one (ADR-0029 §5, step 1).
- Treating the custodian's merge as a promotion would make it D-0024-2, the single signer, entering unannounced. That
  is the ground on which ADR-0033 rejected promoting the reference in place.

After bootstrap a record "changes only through promotion" (ADR-0029 §3). The same workflows then become stage 4 of
the corpus's own promotions, and `tally`, `sign` and `publish` are added.

## Consequences

**Positive**
- **The path ADR-0033 said did not exist is one object**, with each stage's owner named and two stages (intake, and
  signing for every class) newly decided.
- **The corpus root gets an admission rule**, and lineage's `generatedBy` gets a source in Run. Retraining on
  experience becomes a projected, attributable input and not a side channel. ⟨R1⟩ *A return from Run is recomputed
  at intake (IG-4), not taken on the submitter's word.*
- ⟨R1⟩ **Every class's vote opens on gates that read that class** (G-4), and the classes that have none are named.
- **A carrier can be replaced without touching a theorem.** GitHub is one instance. Every authoritative check is a
  script the mechanism owns, which the carrier only runs.
- **f1-tla's working pattern comes home**: thin workflows, scripts that run the same by hand, and results that are
  regenerated and compared, never edited.

**Negative**
- **Every corpus change is a promotion.** A unanimous quorum per intake is slow, and that is the cost of making the
  root decide ingress.
- **The return path is a path for influence.** §4's residual stands: a Byzantine Run principal shapes its
  successor's data, and only Persona verification checks the result.
- **Labelled return waits on another record** (LR-1). Until Build labels, retraining on Run payload is not
  available.
- **Erasure grows a long tail.** An erasure can withdraw promoted artifacts (LR-3). That is expensive and
  disruptive, and it is the honest price of training on erasable data.
- **CI does not prove.** G-3 leaves the proofs to wherever the pinned prover is, and the carrier only says when they
  are stale.
- ⟨R1⟩ **Intake does not check what data teaches** (§3a). For a corpus of any size the veto seats sample, the grant
  seats vote on a report, and the first behavioral check is a Persona's verification after training.
- ⟨R1⟩ **Mechanism code, profiles and seatings cannot promote until their gates are written** (G-4). After
  bootstrap, that blocks every mechanism release until a code gate exists. This is the drafter's choice, and the
  custodian may prefer a declared degeneracy (Options).
