# Evidence and claims

## The results file

One per package series, named `<Series>-results-<yyyy.mm.dd>[b].txt`, generated by a script in the package, redirected
by hand. It is never edited or overwritten. It should regenerate byte for byte on the same machine, except where
something inherently isn't reproducible (trace files named after process ids), and the package README says so.

```text
<one-line title>
Transcribes: spec/Seats.tla (sha256 <16 hex>) · spec/Coupling.tla (sha256 <16 hex>) · ...
Sources: spec/lean/TopakSpec/Prelude.lean (sha256 <16 hex>) · ...
Prover: Lean (version ...) · kernel libleanshared (sha256 <16 hex>) · leanchecker (sha256 <16 hex>) · ...
Theorems (Seats): OnlyThinkersAuthorAlways · OneSeatPerPrincipalAlways · SafeAlways
A theorem holds of the Lean re-encoding, not of the frozen TLA+ text; ...
info: ... 'OnlyThinkersAuthorAlways' depends on axioms: [propext, Quot.sound]
Build completed successfully
Replay: leanchecker --fresh <Root>: every constant <Root> reaches replayed through the kernel in a fresh environment, accepted
```

**The build half** does a clean build (`rm -rf .lake/build`), joins Lake's wrapped `#print axioms` output and sorts it,
so the file regenerates despite parallel build order.

**The replay half.** `leanchecker --fresh <root>` replays every constant the root reaches, the library and
dependencies included, through the kernel in a fresh environment.

**Why the replay is not optional.** A scratch module that adds `False` with `set_option debug.skipKernelTC true` then
`addDecl` builds, and `#print axioms` reports a theorem resting on it as depending on no axioms at all. The replay
refuses it. It is the same kernel in a fresh process, not an independent checker; lean4lean would be one.

**A theorem's name list** comes from a grep with an explicit pattern. If a new module's theorems do not match the
pattern, the list silently omits them, so check it.

## Sync

A script reads the newest results file of each series, and compares each digest on `Transcribes:`, `Sources:`,
`Model:`, `Reference:` and `Floor:` lines with the tree. One row per series, IN SYNC or STALE, exit 1 if any is stale.
It also compares the kernel digest, each `lean-toolchain`, and dependency commits with the pin file, and checks that
the policy the code links is stated.

New module? Add it to the script's module lists, in the package's root import, and confirm it appears on the
`Transcribes:` line, because a module the sync script doesn't list can drift forever.

Two series sharing a source are stale together. If one claim should not depend on another's files, give it its own
series.

## Saying what it shows

| Say | Do not say |
|---|---|
| "Proved in Lean, of the re-encoding of X" | "Proved", "verified", "formally verified" |
| "of a transcription of `f`" | "of the Rust" |
| "of a model of `apply`, replayed against N recorded traces" | "`apply` is correct" |
| "at the module's constants" for a refinement; "at any size" for a model's own invariants | Either without the qualifier |
| "under the semantics of <model>, on the premise that the engine agrees with it" | "the policy cannot error" |
| "The encoding is read" or "checked against the state graph" | Silence on the premise |

Before quoting a result, run the sync check. A results file describes the sources it was built from. If the row is
STALE, the claim is about an earlier version, so tell whoever asked. A dated document can state it. A standing one such
as a README should not carry a status that goes stale by itself: word the claim so it holds as of the results file, or
wait.

Say also what it adds and what it doesn't. A Lean re-encoding removes the unchecked temporal step of the other prover
and adds the encoding premise. It is a different premise, not none.

Mutation rows and witnesses stay with the model checker. A proof that a property holds says nothing about whether the
property can be violated by the mutant it was designed to catch, and nothing about whether the spec has any behaviour.
